** Chez: executable phase programs and dependency compatibility

[[https://cisco.github.io/ChezScheme/csug10.0/system.html][Chez's system operations manual]] distinguishes visit-time code from runtime
revisit code. verify-loadability can check the corresponding dependency closure
and compilation-instance compatibility without running the code; validation
does not guarantee that execution succeeds. Gerbil should learn two things:
make phase programs explicit reusable products, and distinguish their validated
loadability from fresh stateful instantiation. This does not establish that
Chez offers a universal parallel incremental build scheduler or that visiting
arbitrary effectful code is safe to cache as a live shared object.

[[https://cisco.github.io/ChezScheme/csug10.0/use.html][Chez library loading]] also considers library/include changes, with configurable
timestamp policy. The useful lesson is compiler/loader-owned dependency
knowledge. Timestamp checks alone are not the target definition of modernization.

** OCaml: separate consumer contracts, including optimization

[[https://ocaml.org/docs/compiler-backend][OCaml's compilation products]] distinguish compiled interfaces, native objects
and cross-module optimization information. For Gerbil the analogous design
question is which exact product each consumer observes. A syntax export alone
does not cover executable macro helpers, and a stable interface does not imply
stable optimizer observations. OCaml's module semantics are not Gerbil's macro
phase semantics; renaming SSI to a CMI-like format would not establish the
needed independence.

** Dune: incremental planning and execution are different reuse layers

[[https://dune.readthedocs.io/en/stable/explanation/tour/rule-generation.html][Dune's Memo and Action_builder]] distinguish dependency-aware internal planning
from build actions and targets. We infer two Gerbil reuse layers: memoized
semantic dependency/option computation and reusable generated/native products.
The former can remove repeated planning even when the latter hits a cache;
neither permits caching mutable macro instances without an ownership argument.
[[https://dune.readthedocs.io/en/stable/explanation/tour/engine.html][Dune's reusable engine]] also separates rule production from execution. Scheme
should own semantic rules while an executor implements admitted actions.

** Reflection: a composed refactoring, not a frontend configuration

The intended architecture has a producer-owned phase graph, immutable
interface/phase-program manifests, isolated expansion sessions, consumer-specific
readiness, one resource authority and transactional output publication. gxi and
gxc use the same build request/result contracts; live activation is separate.
Modern C remains the native implementation mainline. A Zig candidate must
independently justify replacing a mechanism; these gains do not require it.

Compiler bootstrap builds, user module builds and application activation are
different graphs. Chez's runtime multicore support, OCaml's runtime redesign
and a build engine's parallel scheduling are also different capabilities.
Source repositories and pinned implementation internals for these external
systems remain a follow-up obligation: this pass checked primary manuals and
Gerbil source, and did not audit every external scheduler implementation.

The concrete retirement cuts, added costs and formal gaps live with the
toolchain owner. The user's twelve-core underutilization and reported fivefold
platform difference require decomposition into avoided work, critical path,
worker admission and platform costs; none is proved to be caused by one
particular frontend, operating system or programming language in this study.
