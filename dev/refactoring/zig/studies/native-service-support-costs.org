*Recommendation: modern generated C is currently the better-supported reference for these three services.* This is a scoped planning judgment, not a theorem that C always costs less than Zig. Read the [[file:native-service-support-design.org][complete support/retirement design]].

SC01. These are bottom-up *engineering estimates of this selected source work*, not the earlier arbitrary budget scenarios, measured productivity, statistical confidence intervals or mathematically proven cost bounds. Every WBS row names a source-backed responsibility; its person-day range is the author's low-confidence judgment. Source proves the task exists, not its duration. There is no accepted actual whole-runtime ROI.

SC02. One workday is an experienced engineer's focused effort; 20 days is only a reporting person-month. Assume comparable C/Zig proficiency and the same service capability/caller domain. Include remaining contract work, support implementation, migration, independent review, diagnostics, future acceptance preparation/execution and selected tool integration. No implementation or native qualification is executed in this study. Current research is sunk common work, not charged again as future language-specific labor.

SC03. Scope is a selected Darwin/POSIX service cohort, current Scheme/C producers and admitted C/library leaves, with TLS among selected features. Both routes implement all three new service authorities. The modern C route is funded schema/generator/service reconstruction, not today's unchanged macros. The Zig route really implements service algorithms in Zig with C-facing adapters; it is not an all-runtime/Scheme-backend rewrite estimate. All currently known required support is listed; unknown callers/targets and wider program dependencies are explicit additional tails.

The reporting conversion is C *8.6–17.2 person-months*, Zig *8.8–20.0 person-months*, with estimated paired extra Zig work *0.2–2.8 person-months*. These are cumulative effort, not elapsed schedules and not full runtime rewrite budgets. The paired delta is not obtained by subtracting unrelated low/high endpoints. For each row, Zig shares the same realized common difficulty as C plus the stated language/interface delta. If that coupling assumption is invalid, re-estimate; do not advertise the delta as a proved lower bound.

SC04. Full program cost is ~known scoped work + unknown additional dependencies~, separately for C and Zig. The unknown terms have no finite upper bound established here and cannot simply cancel. Current C reuse makes its scoped case more grounded; source alone does not prove whole-program cost dominance. C-ZT adds whichever independently useful Zig tool is actually selected: none has a specified service-support retirement here, so no benefit or tool budget is invented for it.

SC05. WBS difficulty bands are explicit planning heuristics: a bounded adapter/product change is about 1–4 days; multi-client native integration about 4–12; an owner/phase/failure protocol with independent evidence about 8–20. They are not fitted to line counts. Large unknown proof failures are not hidden inside a two-week upper endpoint. The common support is funded once; RootRegistry, BarrierLog and ReleaseCoordinator totals exclude that shared subtotal. Three domains still need stable-root, bounded-log and task-custody policies, respectively.

SC06. The main plausible Zig reductions are S02/S03, R01, B02/B03 and L02: product construction, residual storage and ordinary local cleanup. Most other work is protocol/caller work that remains, or migration/ABI/tool qualification added by the candidate. Existing TLS/string cleanup and native failure funnels already avoid much of the naive C duplication. The retained patch already fixes per-processor mark_rc placement and provides joined-donor still/RC transfer [SS11]. R02 credits that code in both candidates and prices remaining registry/epoch/reader/receipt work; it does not charge a new scan-placement fix or list splice. Patch text is not loaded-runtime qualification. A private rollback saving cannot be multiplied by six TLS resources, thousands of runtime calls or future clients. The [[file:../../../../docs/experimental/zig/native-service-support-ledger.json][ledger]] includes each task's countercondition.

*** Maintenance Changes and Break-Even

:END:

SC07. Event frequency is unknown; a filtered Git history is not a productivity dataset. The actual NaN-boxing change aca4b9cb on 2025-04-14 touched the selected header, c_intf and mem files. That demonstrates cross-file representation change, not its labor or yearly rate. Do not assume an annual Zig upgrade: a pinned tool may have no such event during the horizon.

| ID / actual change class | C workdays per scoped event | Zig workdays per scoped event | Paired support difference |
|-
| ME01: Add/change a private root/store/task product variant | 1–3 | 0.5–3 | Zig saving 0–0.5 |
| ME02: Change one private allocation/builder rollback path | 0.5–2 | 0.25–2 | Zig saving 0–0.25 |
| ME03: Change owner/epoch/cancel/weak/drain semantics | 3–8 | 3–8 | Zig saving 0–0 |
| ME04: Qualify one compiler/target/ABI upgrade event | 2–5 | 4–11 | extra Zig 2–6 |
| ME05: Update an admitted native library/leaf adapter | 1–3 | 2–5 | extra Zig 1–2 |

SC08. Let I be the estimated extra upfront effort (4–56 days). Count distinct maintenance events over the declared horizon: nV variant events, nE private rollback edits, nT tool/ABI qualification events and nL leaf-library adapter events. Core semantic changes have no language-only saving priced. An optimistic ceiling on support saving is ~0.5*nV + 0.25*nE~ days; extra events cost an estimated ~2–6~ days per nT and ~1–2~ per nL. These are scoped judgment ranges, not evidence of how many events will occur. Net needs actual realized support saving to exceed I plus those extra costs.

| Optimistic saving source | Added qualification events | Extra burden to repay | Strict event-count threshold |
|-
| variant edits, 0.5 day saved each | 0 | 4–56 days | 9–113 events |
| private rollback edits, 0.25 day saved each | 0 | 4–56 days | 17–225 events |
| variant edits, 0.5 day saved each | 1 | 6–62 days | 13–125 events |
| private rollback edits, 0.25 day saved each | 1 | 6–62 days | 25–249 events |

The count range spans the low and high estimated burden; counts are strict (~floor(burden/saving)+1~), not a guarantee. The estimated lower bound of saving per eligible event is zero, so *no finite count currently guarantees positive Zig net*. Even the optimistic threshold requires evidence that these distinct edits are necessary and not already generated/shared by C. An equivalent all-source change touching three services is one common support event unless it really creates separate residual work.

SC09. This changes the working decision: stop treating added consumers as proof that Zig will pay for itself. Use modern generated C as the present reference for these services, retain Zig as a revisable alternative, and price each actual boundary change. Reconsider if qualified reusable Zig support or team/tool evidence removes named positive-delta rows, or if recurring support changes genuinely exceed the threshold. This is a source-informed choice under low-confidence estimates; full runtime economics and native admission remain open.
