The previous framework asked whether all five audit needs were covered. The
separate outcome DSL knew that leaf/support REVs do not close an integration,
but =RevisionSubmission.admit= never joined that condition. A detailed comment
could therefore accompany a fragment without closing its architecture result.

The [[file:models/sysml/submission-units.sysml][submission component]] and common SysML gate policy now require one declared
unit. Python's existing =project= reads the component and programme using native
SysML. It does not maintain a second list of result IDs/requirements. The
existing ASCENT commit policy requires unit coverage AND all five gates.

| Unit | Required evidence | Progress permission |
|------+-------------------+---------------------|
| integration | Whole result, all predecessor obligations, every declared source/native case, actual runtime/generator change | Exactly one complete result |
| support | Exact declared non-runtime paths; normal five gates and real scoped tests | Zero; no result ID |
| missing/unknown unit | Rejected before audit/admission | None |

The changed paths come from the selected Git tree, not a caller path list.
Runtime/header/generator semantic code cannot be relabelled support; wildcards
cannot authorize a broad path surface. Mechanical source changes outside the
support surface require an explicitly designed whole delivery, rather than an
informal exception. Existing historical models/receipts remain historical;
a future component must explicitly adopt the unit contract.

** Source-bound observations :custody:

An integration producer supplies =deliveryEvidence= as a repository JSON path.
It binds result, base revision, tested source tree and profile, with exactly one
observation for every projected requirement. Every observation names a durable
receipt, its actual digest and pass status. Each receipt must be complete,
bind the same identities and list the requirement it covers. Missing, duplicate,
failed, stale, private-cache or outside-repository evidence refuses admission.
Re-read the contract at audit review, admission and Git submission: changing a
receipt after review cannot silently change the delivery.

Framework-source support has an explicitly narrower qualification scope. It can
publish only its exact tested framework sources and evidence in the framework
repository, and cannot authorize vendor/native integration. Its receipt states
that complete native-source equivalence has NOT been established. This allows
the framework to test its own enforcement without pretending Python tests are
Gambit runtime tests or staging unrelated SMP changes.

** Boundary and counterexamples :questions:

- Five gates all green, one lifecycle obligation absent: reject the integration.
- Current lifecycle cases pass, a root/collector predecessor case absent: reject.
- Only documentation/tests changed but a result increment claimed: reject.
- Runtime source hidden behind support, a wildcard or unlisted path: reject.
- Source/profile/result mismatch, duplicate/failed observation or receipt drift:
  reject; retain the previous source and unrelated index/working changes.
- A valid support correction may commit, but produces no progress permission.

This verifies evidence joins and source custody, not the truth of arbitrary JSON
or an exhaustive C weak-memory theorem. Source/native review remains necessary.
A human or another tool can invoke raw Git outside Python; the framework cannot
prevent that. Agents must use the audited entrypoint. No repository-wide Git hook
or claim that LLM behaviour is mathematically constrained is introduced.

** Benefit and cost matrix :matrix:

| Mechanism | Removed failure mode / benefit | Added work and limit |
|-----------+-------------------------------+----------------------|
| Unit gate joins commitReady | Five-gate completeness cannot hide missing architecture closure | One relation join and source-bound requirement coverage |
| Programme closure from SysML | Component cannot silently omit predecessor requirements | Native projection; no duplicated QNT/Lean |
| Exact support paths | Helper/setter runtime work cannot be disguised as support | Git tree diff plus explicit source role |
| Re-read durable receipts | Changed/unknown result cannot retain old approval | Hash/JSON checks at review and commit |
| Progress permission | Support or repeated leaf commits do not advance2/4 | No runtime speedup or architectural outcome from this mechanism |

The [[file:models/sysml/owned-lifetime.sysml][owned-lifetime component]] deliberately has no passing runtime receipt. It
projects9 programme requirements (3 roots,3 collector,3 lifecycle),5 source cases
and8 native cases:22 obligations. These must close together before progress can
advance from2/4 to3/4. The independent SMP ledger remains1/12.

| Ownership segment | Real source / consumer to reconcile | Full exit criterion |
|-------------------+-------------------------------------+--------------------|
| Request root through resize | =lib/setup.c:___current_vm_resize=, generated Scheme entry | Freeze/reload live request roots before native creation and allocating calls |
| Physical reserve and initialization | Current resize/section allocator, pending setup prototypes | Exact slot/stack/heap reservations and initialized descriptors before members publish |
| Member and VM publication | Setup/registry callers and owner execution entries | Release/acquire publication; no failed/uncertain child becomes a normal member |
| Writer, root and worker drain | Existing RC/RootOrigin/RootTask, write authority and owner exits | Stop/close facts discharge their own debts; timeout is not owner death |
| Affine cleanup and unknown join | Cleanup callers and =unknown-join-worker-domains.scm= | Retain uncertain resources/roots; healthy VM GC continues; global free remains denied |

Pending registry/lifecycle/write-authority files are unqualified prototypes,
not implementation evidence. Their predicates and fields must be reconciled
against the published root/collector contracts, then validated as one source
cohort. Do not merely stage those files or transplant repair-line patches.
Keep Scheme shared values, precise frames, tail dispatch and multi-shot
continuation as the runtime contract. Scheduler/request-product work belongs
to the fourth integration result. No heap, deadline or sleep increase qualifies.
