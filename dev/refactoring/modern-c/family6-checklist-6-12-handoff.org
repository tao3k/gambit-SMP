** P1 refactoring decision: distinguish GC completion from allocation admission
:PROPERTIES:
:CUSTOM_ID: family6-p1-gc-resume-contract
:END:

Start at the first failing allocation and preserve its exact seed, configured
prelude, request and collection round. The recorded epilogue and exception
identify a return boundary. A =GC-STILL= tag and a cursor past the soft
limit do not identify which allocation contract first failed. The earlier
=n+k= planning refusal is a separate branch in =copy-planning.inc=.

[[https://3e8.org/pub/scheme/doc/larose-feeley-incremental-gc-1998.pdf][Larose and Feeley (1998), sections 3.2 and 3.4]] describe movable allocation within a section,
still allocation from the C heap, and a physical reserve beyond a movable
limit. [[https://www.cs.tufts.edu/~nr/cs257/archive/marc-feeley/polling.pdf][Feeley (1993), sections 5 and 7]] relates runtime checks to calling boundaries.
Apply these distinctions to the current implementation by checking the
allocation being resumed at the return boundary and retaining bounded
polling. The old section and reserve sizes are historical.

| Boundary | Current vendor implementation | Required postcondition |
|-
| Copy plan | =copy-planning.inc:plan_copy_round= checks the representability and actual mapped capacity for =n+k= before copying. | A rejected plan retains the old roots and owns no new copy destination. A successful plan owns a specific round's copy capacity. |
| Still reservation | =capacity-resize.inc:resize_heap= can roll back =requested_words_still= on capacity or backing refusal. =object-allocation.inc:alloc_scmobj_still= uses GC success to proceed with the C allocation and refunds =words= on allocation failure. | Authorize the still caller only when this request's reservation exists. Transfer the charge once on allocation or refund it once on failure, preserving the existing deferred charges. |
| Movable resume | =memory-lifecycle.inc:prepare_mem_pstate= computes a soft slice and clips it at the hard limit minus the reserve. =allocation-limits.inc:___heap_rearm_after_collection= can accept =hp<=heap_limit= without validating a pending demand. | Publish the current processor's heap interval and epoch. A write group's full aligned footprint must be admitted under that view. Refill under the existing locked claim or return a bounded refusal. |

The current =collection-round.inc= epilogue can clear =overflow= after
movable rearm when =max_heap==0=. A still request may therefore see an
allocation success after =resize_heap= rolled back its charge. The
early plan-refusal branch that returns success after growing the pool also
needs to establish the caller-specific reservation before reporting success.
These are source obligations. The retained P1 description does not prove
either branch was taken by the failing seed. =max_heap==0= removes the
configured cap, while backing allocation can still fail.
