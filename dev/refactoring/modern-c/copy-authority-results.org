The section-owned gate observations below remain predecessor evidence;
they do not qualify later capacity or foreign-writer changes by inheritance.

The current source authorizes copying before changing an arena or retiring a
section. Previously, =mark_array= reserved/refilled first and then competed on
the source forwarding header. Its losing CAS could refund the private grant
without recovering the section already closed by refill. This is a physical
capacity problem, not simply a missing bounds check.

The [[file:models/sysml/root-worker-exit.sysml][SysML authority]] now specifies one gate owned by each physical source
=msection=. The validated source coordinates select that owner; there is no
fixed hash-table cardinality or per-object identity record.
Under the gate, the copier reloads the source header, reserves space and publishes
forwarding. It releases before copying payload or processing children. Another
contender observes forwarding without reserving another interval. Distinct
objects in one source section remain distinct and serialize only this fragment.
Captured stack-frame construction retains the existing frame-access protocol.

The former =GC_COPY_GATE_COUNT= value 64 was a heuristic without a measured
choice or a derivation from worker count, source count, cache geometry or a
capacity theorem. It was not a correctness parameter. The candidate now removes
that macro, VM array and address-modulo path, rather than exposing the same
unjustified number as a configuration option.

Physical source ownership is an explicit architecture choice, not a proof of
optimal granularity. It aligns lock lifetime and metadata accounting with the
allocation unit. More objects in one section can cause more contention; payload
copy remains outside the gate. Finer ownership would require its own mapping,
lifetime, memory-budget and performance evidence.

The source header uses the existing acquire-load service. Permanent headers may
reside in read-only module storage, so an RMW used as a load is unsuitable. The
selected GCC backend supplies a real atomic load. =load_copy_source_header=
uses a gate-protected ordinary read on the legacy fallback, so its RMW load
implementation is never applied to a possibly read-only permanent header.
This fallback is source-reviewed, not qualified by a non-GCC platform execution.

** Conditional source argument :refinement:

#+begin_quote
Within one frozen round, all admitted ordinary object-forwarding writers use
the same section-owned gate for a source header. That header changes monotonically from the
original header to forwarding. Revalidation and forwarding occur under the gate,
and only a successful revalidation can reserve. Therefore a duplicate managed
contender cannot consume a second reservation or retire a section for this copy.
#+end_quote

The premise excludes raw native header stores and unclassified reentrant custom
allocators. The gate is not a stop receipt. Unknown copier exit retains the
round and its pending initialization/Tail; neither a timeout nor a new epoch may
clear that debt. The existing defensive CAS-loss refund remains for a bypass
writer, without extending capacity admission to that writer.

Forwarding publication still precedes payload readiness. The winner retains
initialization and Tail ownership until the existing commit path completes;
another scanner cannot derive payload readiness from forwarding. The nested
order is frame access, copy gate, then allocator/FIFO gates. FIFO consumers
release their gate before scanning. A copy-gate holder must not scan children or
acquire frame access. General allocator callback effects remain a separate
admission obligation.

The complete physical peak must account for copied live intervals, headers and
alignment, chunk bookkeeping, successfully retired section tails, W active
arenas, R restored stacks, context resume grants and unknown-retained grants.
Removing duplicate requests does not prove a bound on that sum. The fallback
from requested W to W=R still cannot substitute for full pre-flip placement.

** Net-work condition and counterexamples

The conditional work saving is the eliminated duplicate reserve/refill/refund
work, minus header-load, gate and same-section waiting overhead. Positive throughput
benefit requires the former to exceed the latter. For D=0 there is no duplicate
reservation saving; many unrelated objects in one source section can also lose time.
No measured crossover or cycle cost is available here. The separate structural
benefit is removal of an adversarial duplicate-dependent physical waste term
from the capacity proof, without restricting multi-shot continuation semantics.
