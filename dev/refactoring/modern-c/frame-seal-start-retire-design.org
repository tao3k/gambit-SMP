A private FrameSpec seal must close the whole reachable mutation capability,
not just the constructor's seven fields. A compiler continuation is not a
once-only guard. Native ABI compatibility is not an immutability guarantee.
The runtime capacity receipt needs one generation/phase authority for revocation
and copying start, followed by a distinct descriptor-detachment obligation.

* RESEARCH Source-ground writer closure
** Direct writers and shared containers
The active FrameSpec constructor validates exact kind/size/link/gc-map and
returns a mutable vector. Three return wrappers construct it. In the bounded
C-target files, =targ-add-label= is the actual class/info replacement writer;
there is no discovered dedicated setter for a FrameSpec field. This negative
lexical result does not prove arbitrary vector mutation impossible.

The canonical label table, ordered queue, code stream and val-lbls share label
vectors and mutable number cells. Procedure =set-car! p= publication precedes
final goto numbering. The module procedure work queue must drain as well.
The count traversal, code dump, IFD descriptors, OFD headers and root-map chunks
must all consume one finalized private graph and ABI identity. Required output
serialization remains; only redundant validation/count/profile work may disappear.

** Additional real writers beyond the FrameSpec vector
- =target-add= can replace registry payloads; =target-select!= selects mutable
  target hooks and writes global target.* fields. The C target begin hook sets
  register/layout options; its end hook returns without restoring a session.
- =targ-dump= destructively clears the four c-intf collections and owns their
  former declaration/procedure/initializer/object data. These containers and
  provider closures belong to the private session's alias closure.
- =targ-start-dump= installs global output/line/source state. =targ-end-dump=
  closes the output port on its normal path. Info-port/current-output-port and
  ordinary display calls are external effect boundaries. A capturing or
  reentrant output callback specifically carrying FrameSpec has not been shown.
- =cf= and =compile-program= use =with-exception-handling=. That function captures
  a continuation, writes the global throw handler, runs proc, then restores the
  old handler. =compiler-abort= invokes that continuation. Frontend target/env
  teardown is sequential. These real nonlocal paths do not constitute a
  multi-shot-safe owner/commit/cleanup protocol.

The [[file:../../../evidence/research/frame-seal-start-retire/source-witnesses.json][source snapshot anchors]] and [[file:../../../evidence/research/frame-seal-start-retire/writer-inventory.json][eight scoped writer inventories]] include backend writers,
frontend handoffs, callbacks, FFI generation and loader cleanup. Their scope is
explicitly bounded: no whole-program points-to or arbitrary-extension theorem.

* RESEARCH Continuation restoration and transaction identity
=macro-expand= invokes a runtime-evaluated expander; =scheme-global-eval= creates
that procedure. Ordinary macro expansion precedes creation of backend FrameSpecs.
A macro continuation may therefore retain frontend state and later reexecute
the backend; this is not by itself a direct alias to an existing FrameSpec.
The compiler's own exception continuation is a separate witnessed control edge.

A proposed construction guard has SessionId, construction generation, phase,
owner identity, rooted candidate and output transaction identity. A suspension
retains the candidate and its roots but relinquishes mutable execution authority.
A legitimate resume acquires the same still-live generation and suspended phase.
Once sealed or aborted, the generation advances; stale or duplicate restoration
cannot reopen writer authority or repeat a completed output commit.

Multi-shot continuation support has two different admission cases:
1. A still-live suspended construction resumes under its owner guard. A second
   simultaneous/duplicate entry has no second writer permit.
2. A captured computation restored after publication needs a distinct private
   session/fork with its own mutable provider and output state. It may share
   immutable semantic data. Side effects and their ordering need a separate
   replay/fork contract; the current model does not establish that equivalence.

Rejecting stale service credentials is an optimization/service admission rule.
It is NOT a proof that rejecting an arbitrary legacy Scheme continuation keeps
all Scheme behavior unchanged. Unrestricted effects/cross-boundary continuations
must keep their legacy semantics or be routed away from certified reuse; total
fallback equivalence remains OPEN. Adding dynamic-wind alone neither makes a
reentered cleanup once-only nor restores all mutable compiler globals.

An abandoned or failed unpublished candidate is released only after its root,
continuation and native leases are detached. Published/unknown output remains
owned by its stable transaction record. A resumed frame cannot manufacture an
ownership receipt simply by holding an old numeric SessionId.

* RESEARCH FFI escape and registered capability boundary
=c-lambda= and =c-define= build emitted C wrappers. Their presence in input does
not mean the emitted native body executes during that same compilation. Macro
execution can call already available native procedures, which is a separate
capability path. The generated scheme-object modes and SFUN marker/call macros
show that native code and nested callbacks can carry Scheme values.

No direct FrameSpec-to-native argument/store was found in the bounded source
slice. Treat it as an unresolved possible escape under unrestricted extensions,
not an observed bug. A modern C sealing profile must distinguish:

| Exposure | Admission | Custody |
|----------+-----------+---------|
| Scalar values or copied serialized snapshot | Permitted after validation | Receiver owns copy; no shared mutable compiler graph |
| Read-only descriptor view with registered rooted lease | Conditional | Stable guard pins object and code generation across callback/GC |
| Mutable borrow while construction owner is live | Conditional before close | Borrow must end before writer-closure receipt |
| Raw Scheme vector/body pointer or untracked saved C value | No certified seal/reclaim | Retain legacy/conservative path and descriptor lifetime |
| Native return/cleanup result unknown | No release credit inferred | Keep stable record, root and old descriptor pinned |

The Scheme-level private vector must not be returned through the unrestricted
FFI as though it were physically immutable. Cooperative typed native APIs or a
copied native representation are necessary. Malicious/privileged raw C access
cannot be sandboxed by C's const keyword. =___release_scmobj= adjusts still-object
reference counts; it does not prove old code/OFD detachment, and a native raw
movable pointer still needs the actual GC-root/reload contract.

* RESEARCH Single authority for issue, revoke and copying start
** Proposed linearization contract
A stable VM collection control record outlives every observer. It holds a lease
on the independently owned process-global descriptor record; copying arbitration
and global code retirement are separate authorities. The abstract ledger groups
these obligations but does not implement their two-authority C11 composition.
 Its atomic authority binds
collection/module/source generations, phase, winning owner/guard identity and
admitted credits. Immutable payload/root registration and descriptor leases are
completed before ISSUED publication. Generation/counter exhaustion rejects
reuse; the authority cannot wrap into an old identity.

#+begin_example
prepare rooted payload and stable finish guard
    -> release publish ISSUED(generation, payload identity)

starter: acquire protected control observation
         CAS ISSUED(generation) -> STARTED(generation, winner guard)
revoker: CAS ISSUED(generation) -> REVOKED(generation)

revoke wins: stale starter CAS fails; settle observer without copying
start wins: revoke cannot free/replan; stable guard retains copy/root/code credit
known finish: settle copy credit and drain permitted users
unknown finish: retain; no implicit refund, retry or descriptor release
#+end_example

Both transitions must modify the SAME authority object. If a separate valid flag
is read before copying, a release/acquire pair does not make that check-and-start
atomic. A successful start CAS transfers an already registered observer/guard
credit to copying, without an allocation or unprotected interval. Failed CAS
must inspect its refreshed expected value and revalidate generation/phase;
spurious weak-CAS failure is not proof of revocation. The design chooses strong
CAS for the explicit two-way decision and allows bounded retry of unrelated
credit changes, without assuming lock-free availability on every C platform.

** C11 obligation table
| Operation | Proposed order | Required additional proof |
|-----------+----------------+---------------------------|
| Initialize private immutable payload | Ordinary writes before publication | Owner excludes mutation; roots registered across safepoints |
| Publish ISSUED | Release store/RMW under exclusive issuer | Stable authority and exact generation/ABI/source tuple |
| Start/revoke successful CAS | acq_rel | Same atomic object and expected identity; credits transferred once |
| Failed CAS / protected observation | Acquire | No use of unpinned payload; generation/phase recheck |
| Close user admission | acq_rel authority transition | No independent late registration after the final-zero observation |
| Return credit | acq_rel RMW under registered guard | Known completion; no unrecorded decrement or duplicate return |
| Final drain and reclaim | Acquire observation after admission close | Zero users, no pending/unknown guard and no future code reentry |

A short owner lock can also realize the abstract arbitration if the critical
section excludes allocation/callbacks and does not span copying or GC waits.
CAS is a candidate translation, not an established throughput advantage.

The abstract ledger is NOT a verified finite-bit encoding of these fields. A
production control-word representation, per-user receipt recording, arbitrary
processor product, and interrupted CAS/credit-return reconciliation still need
C11 refinement. The current model permits one registered starter observer per
collection decision; a scalable multi-starter variant requires additional proof.

C11 reference: [[https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf][N1570]] sections 5.1.2.4 and 7.17.3/7.17.7.4 distinguish
ordering, synchronization and CAS outcomes. Acquire/release cannot substitute
for object lifetime. [[https://research.ibm.com/publications/hazard-pointers-safe-memory-reclamation-for-lock-free-objects][Michael's hazard-pointer paper]] motivates protecting readers
before reclaiming removed storage and accounting for delayed readers/ABA.
This study does not claim a hazard-pointer implementation or transfer that
paper's progress/performance results to Gambit.

* RESEARCH Exact release condition for old descriptors
The model field =reclaimed= denotes completed *local* retirement/detachment.
It never authorizes process-global dlclose by itself. A descriptor generation
can actually be unloaded only when all of the following hold:
- Public/module/FFI/maintenance/root admission is closed for that generation,
  including queued resize roots and deferred work that could acquire it.
- No issued capacity receipt or active copying owner can still use its layouts.
- No live captured frame/continuation, closure, denv or restored computation can
  reach its code/OFD; an inactive multi-shot continuation is still a user.
- All native borrows, in-flight callbacks and observers are known detached.
  No unknown guard, delayed return or unacknowledged handoff can revive a user.
- GC relocation/scanning and maintenance-derived work have relinquished their
  descriptor leases under the same generation and admission-close authority.
- All other VMs and process-level native owners are detached. =___dyn_mod= is
  a process-global owner; a single VM receipt does not establish this condition.
- The loader's handle ownership and any native finalizer/OS callback/teardown
  dependencies permit actual code unload; GC heap liveness is not that receipt.

These conditions require a complete consumer inventory. Existing =os_dyn.c=
=cleanup_dynamic_load= walks a global dl_list and unloads handles at cleanup.
The two =os_setup.c= callers are failed setup unwinding and global =___cleanup_os=.
The failed-load dlclose branch is distinct: it does not establish safe retirement
of an already published module. The global dl_list also prevents treating
per-VM collection epochs as the sole code-retirement identity. Neither is an existing per-generation hot-reload
protocol. This research does not allege a current concurrent-unload execution;
it identifies contracts needed before introducing earlier reclamation.

Source-slot ACK, processor exit, closing a module's public entry, a zero still
refcount or returning from one callback is insufficient by itself. Pending
VM resize thunks may alias ledger/context roots and transitively retain old
continuation descriptors. Those roots remain in the preceding canonical source
budget B and live producer-summary union. Descriptor release cannot revoke a
copy capacity receipt underneath an active collector.

** Counterexamples retained
1. Read ISSUED; revoke; start from the stale boolean: both decisions appear to win.
2. Restore the captured writer continuation after sealing: immutable contract reopens.
3. Seal while a raw mutable native alias survives: private publication is not private.
4. Reclaim after source ACK while a captured frame still retains old OFD.
5. Close admission and see zero, ignoring an earlier protected observer.
6. Treat unknown native cleanup as a successful return credit and reclaim storage.

* RESEARCH Net benefit and retirement sequence
The [[file:frame-seal-start-retire-matrix.org][derived matrix]] includes necessary work and positive-benefit conditions.
Let k be redundant descriptor-summary traversals and F the label count. Saving
requires saved summary work to exceed O(F) private copy/validation plus
invalidation; code/IFD/OFD serialization is still necessary. Per-generation
memory benefit requires reclaimed old code/data to exceed lease, summary and
unknown-retention storage. CAS contention and additional roots can erase a
throughput benefit. No percentage or person-day estimate is claimed.

Migration order: own compiler target/c-intf/ports; establish private producer
contract; root stable session and native guards; serialize issue/start/revoke;
introduce complete user credits; then qualify per-generation descriptor detach.
Only afterward may shared target globals, duplicate layout derivation, split
valid/start flags or global-only lifetime assumptions retire on admitted paths.
No current C path is retired by these documents. Modern C supports this complete
contract; this study establishes no additional Zig benefit.
