*** 1. Research Direction and Comparator Roles
:PROPERTIES:
:ID: 50676786-396f-5120-92a1-c1bbf130b6b9
:CUSTOM_ID: 1-research-direction-and-comparator-roles
:END:

*The primary candidate is a complete Gambit native-boundary reconstruction.*
A patch-sized root guard is a control, not the ceiling of Experimental research.
Existing Scheme semantics, libraries, proper tail calls, continuations and GC
are core assets. Existing C emission, implicit root/entry assumptions and internal
ABIs can be replaced where the new architecture warrants it. Whole-cohort
recompilation and explicit migration costs are allowed; indefinite compatibility
wrappers are not an adoption objective.

Use four comparisons with distinct meanings:

| Comparator | Meaning | Decision it can inform |
|-
| B0 | Current source/configured architecture, with exact repaired candidate/installed identities kept separate | Total modernization opportunity and actual migration baseline |
| Bmin | Existing candidate plus bounded RC/marker repairs | Cost/capability floor; avoids inventing work already solved; cannot veto a larger demanded design |
| C-full | Same complete semantic/runtime/provider/service design implemented in modern/generated/opaque C, with necessary C++ provider support | Architecture benefits versus implementation-language increment |
| Z-full | Zig owns the native system plane over the same complete Gambit contracts and qualified providers | Candidate under study; positive net benefit still needs a certificate |

C-ZT remains the C-full variant with the same independently selected downstream
Zig tool. LLVM and MLIR are provider choices, not aliases for the Zig language.
Calling a C compiler from build.zig is not the complete candidate. Conversely,
no-GC Zig does not require removing Gambit's managed collector. User-directed
scope expansion changes the design question, not the standard of evidence.

The [[file:../../runtime/ffi/studies/rc-marker-minimal-contract.org][RC/marker minimum]] remains a source-grounded
control. Its wrapper-only countermodel does not establish that Z-full is
nonpositive. Likewise, a positive total LLVM modernization opportunity would
not prove that Zig beats the same C-full architecture.

*** 2. What Modernization Must Mean
:PROPERTIES:
:ID: 65922a0c-a8b6-516f-a637-d956b1668923
:CUSTOM_ID: 2-what-modernization-must-mean
:END:

| ID / objective | Architectural commitment | Evidence/acceptance dimension |
|-
| MA01 semantic authority | Scheme issues binding, evaluation, effect, root, control and initialization meanings once | Complete selected operation/primitive/FFI domain; no late hidden semantic decisions in renderers |
| MA02 independent runtime ownership | VM-owned root/continuation carriers, exclusive execution, collective participation and last-return lifetime are distinct | All state transitions/root updates/last uses closed; detached or failed-retirement capabilities separately justified |
| MA03 direct native products | Admitted native route emits LLVM objects/bitcode and Gambit metadata without generated Scheme-host C | Selected C generation/preprocessing calls genuinely disappear; exact module/constant/setup/control semantics retained |
| MA04 high-level optimization | Preserve nested functions, mutable identity, effects and capture before closure/storage choices | Each higher-order/escape/region transformation has semantic preconditions and rejection cases |
| MA05 replaceable upstream services | Delegate machine code, target layout, supported object mechanics, admitted transformations and debug infrastructure | Provider capability/version boundary; no project clone of ordinary backend mechanics |
| MA06 coherent artifacts | Semantic products, runtime-protocol products, provider IR, target objects and loaded instances have distinct identities | Correct dependency closure and fresh mutable instances; cache hit is not initialization or lexical identity |
| MA07 diagnosable operation | Native sessions expose source/point identities, ownership, failure stage and retained diagnostics | Debug/root/continuation interpretations remain distinct; failures survive cleanup and provider replacement |
| MA08 sustainable retirement | One owner per migrated decision; obsolete C emission/layout/config/foreign paths actually leave the selected domain | No live selected caller through retired policy; legacy cohorts explicitly bounded and priced |
| MA09 sufficient economic leverage | Total modernization and Zig-specific incremental value are both argued against fair controls | Independent cost/capability ledgers and conservative bounds; correctness is a hard condition, not a weighted score |

These are nine proposed objectives, not nine implemented capabilities or a
numeric modernity score. Multicore execution, parallel GC, latency, VM isolation,
serial cost and maintenance are distinct axes. Neither a modern syntax nor
LLVM linkage alone satisfies this vector [MS01-MS10, MP01-MP12].

*** 3. Full Responsibility Split
:PROPERTIES:
:ID: 41568092-b6a8-5867-9410-abbf4dbc529a
:CUSTOM_ID: 3-full-responsibility-split
:END:

| ID / owner | Retained / new responsibility | What it does not independently decide |
|-
| SO01 Gambit Scheme frontend | Parse/expand/declarations/bindings/evaluation order, typed ForeignPlan capture before registry reset | Native target layout or machine instruction selection |
| SO02 Scheme semantic compiler | Pre-normalization high semantic export; G3 completed HostGraph/FrameSpec/PointId/effects and runtime-role meaning | Recover missing roots/control from generated C or LLVM register liveness |
| SO03 Gambit runtime protocol owner | Values, root/update law, continuation/call semantics, execution/participation/lifecycle and module instances | Delegate these semantics to Zig allocator or stock MLIR effects |
| SO04 Zig system plane | Validated native requests/profiles, sessions/resources, common physical realization, provider adapters, product/diagnostic/custody and native SDK construction | Become another Scheme semantic/configuration resolver |
| SO05 MLIR semantic service | Implement admitted high-to-low transformations and explicit legality/verifiers under Scheme-issued meaning | Invent nonlocal-control, dynamic binding, GC or foreign effect laws |
| SO06 LLVM/target service | Instruction selection, register allocation, target object mechanics, admitted optimizer/LTO/debug facilities | Materialize Scheme identity, root objects or initialize a VM automatically |
| SO07 C ABI / legacy-control island | System library ABI, supported raw-C interfaces and contained existing nonlocal C behavior | Force all new runtime paths to retain the old generated macro/control protocol |
| SO08 runtime mechanism implementations | Selected C or Zig implementations of root/context/entry/module mechanisms; collector engine behind explicit interfaces | Rewriting the collector algorithm solely because its implementation is C |

SO03 is semantic/runtime ownership; SO08 is implementation choice. The complete
candidate permits moving concrete C mechanisms into Zig when ordinary/control
contracts permit and a named C owner retires. It does not mandate an immediate
collector rewrite. A separately justified collector algorithm can later consume
the same root/update/participant interfaces, with its own semantics/cost gates.

*** 4. Shared Runtime Contract: A Larger Experimental Candidate
:PROPERTIES:
:ID: aaac9167-936d-53d7-a70d-723e64f2128a
:CUSTOM_ID: 4-shared-runtime-contract-a-larger-experimental-candidate
:END:

The following are logical contracts, not ABI structs or implemented APIs:

#+BEGIN_SRC text :eval never
SharedRuntimeContract {
  value_and_object_protocol,
  frame_control_and_continuation_protocol,
  root_slot_and_collector_update_protocol,
  execution_context_and_participation_protocol,
  foreign_effect_and_nonlocal_origin_protocol,
  module_instance_code_and_descriptor_lifetime,
  capability_and_version_manifest
}
VmRootDomain {
  vm_incarnation,
  retained_root_segments,
  published_context_carriers,
  scan_admission_and_epoch,
  mutation_update_and_withdrawal_law
}
ExecutionContext {
  context_identity, vm_identity,
  exclusive_execution_owner,
  runtime_owned_frames_and_saved_roots,
  participation_state, return_origins,
  code_descriptor_and_native_resource_custody
}
RetainedRootHandle = (vm_identity, slot_identity, slot_generation)
#+END_SRC

Stable retained slots can live in VM-owned segmented storage with explicit
initialization, publish, update, close, last-reader withdrawal and reuse rules.
Handle identity is not a raw tagged value or a permanent heap address. Generation
checks do not replace valid VM lifetime/execution rights. Generated SSA values
need not all become handles: mapped Scheme frames and proven local values can
remain direct within their admitted extents. The purpose is one declared root
law across temporary frames, retained FFI values and suspended contexts, not an
indirection on every arithmetic operation.

This is deliberately broader than MP1's saved0 repair. Current RC headers can
be a legacy carrier adapter; new retained-foreign values use the VM root domain.
A new managed foreign route cannot bypass the update API through raw data stores.
Current/possible future collector barriers belong in that API and selected
profile. No particular generational barrier algorithm is assumed already present.

**** Execution, roots, participation and reclamation
:PROPERTIES:
:ID: 0b09d23b-4b9e-5587-9c16-cb85aaab5326
:CUSTOM_ID: execution-roots-participation-and-reclamation
:END:

| State | Execution / root / participation contract | Transition obligation |
|-
| CT0 OwnedActive | One execution owner; live values in admitted local/frame/root extents; active collective member | No competing host mutation of same context |
| CT1 Publishing | Finish frame/root/update publication; native input/output custody fixed | Serialized with current collective request; partial state not detached |
| CT2 ParkedNative | No managed access/callback; VM-owned carrier remains independently scanned; participant transition acknowledged | Original return/VM/code lifetimes retained; native wait may continue after acknowledged membership transition |
| CT3 ReentryPending | Pending request/owner/VM validity reconciled before Scheme work | Reacquire execution/participation, reload moved values, then allocating conversion |
| CT4 Retiring | New entry closed; execution and carrier readers/return origins have distinct drains | Publish a surviving root custodian before any old carrier is reclaimed |
| CT5 RetainedAfterFailure | Known published carrier retained; state uncertainty and live native users explicitly recorded | GC enumeration requires proven publication/no-mutator condition; teardown remains blocked by live/unknown native use |
| CT6 Reclaimed | No admitted scanner, native return, execution, code/map or slot reader remains | Invalidate identity and release storage only after actual last uses |

CT2 is a *new capability*, not a spelling change for current BW1 select or a
processor-count decrement. A request/member state machine, scanner enumeration,
weak-memory publication, cancellation/reentry and failure semantics must be
designed together. Existing participating waits remain a comparator and migration
adapter. The candidate's successful RC/still transfer is credited.

Independent VM root carriers can address the structural dependency highlighted
by pending retirement: roots need not disappear from enumeration merely because
an execution processor leaves the active cohort. They do not magically make an
unjoined possibly mutating host safe. CT5 GC progress is admissible only when
root publication and prohibition of further managed mutation are established;
VM/code/C-return reclamation can remain blocked even then. Unknown state is not
converted into safe detachment by retaining memory [MS08-MS10].

**** Continuations and foreign control
:PROPERTIES:
:ID: aeed6bfd-0575-56f8-a3b2-337e9c0b1403
:CUSTOM_ID: continuations-and-foreign-control
:END:

Scheme continuations remain runtime objects/frames with explicit capture,
restore, dynamic-environment and multi-shot/foreign-origin semantics. New typed
native service operations can deliver structured outcomes such as ordinary
return, Scheme error, suspend or transfer to a known Scheme continuation/origin.
That enables a modern explicit boundary; it is not a replacement of arbitrary
C callback nonlocal exits by an integer status.

A foreign library expecting an ordinary C callback result may keep executing
observable actions if a nonlocal Scheme transfer is naively returned as status.
Therefore cooperative typed APIs can use explicit outcomes only under their
complete effect/control contract. Raw C invocation and all potentially crossed
legacy C frames remain inside an admitted C control island; an outer Zig frame
must not be skipped. Translating an escape after a correctly completed C unwind
needs a proved mapping of the original return origin and cleanup semantics.
Old C macros/control can retire on the complete new typed cohort; raw C ABI
and supported legacy behavior are retained and priced where still needed.

*** 5. Two Semantic Routes, One Runtime Realization
:PROPERTIES:
:ID: 9c3429b9-bc94-5d19-b497-b8e5df0e203a
:CUSTOM_ID: 5-two-semantic-routes-one-runtime-realization
:END:

The existing high-level study selects export immediately before normalize-program
(after lst/env/c-intf exist), with a parse-time typed FFI side product. This retains
nested functions/mutation identity before primitive expansion, boxing decisions,
beta reduction and lambda lifting. The lower route uses GVM plus G3 completion
of roots/checks/control that currently emerge during C emission [MS01-MS05].

#+BEGIN_SRC text :eval never
HighSemanticProduct -> admitted higher-order/effect/escape transforms
                    -> explicit control/closure/allocation plan --+
                                                               |
GVM + Scheme G3 completion -> HostGraph + FrameSpec --------------+
                  -> one SharedRuntimeContract-bound physical realization
                  -> direct LLVM OR admitted MLIR-to-LLVM lowering
                  -> native object + root/control/module/debug products
#+END_SRC

This defines the full optimization opportunity; D0/minimal C remains a reference,
not a prerequisite that limits the architecture. D1/mixed-tail capabilities still
need complete cycle/ABI/target evidence. LLVM IR cannot replace mandatory Scheme
stack/control transitions with ordinary native recursion or optional tail hints.

Proposed high operations describe lexical closure/environment identity, generic
apply/tail-apply, mutation/effect order, allocation/escape, continuation capture/
transfer, foreign entry and relocation points. Operation names/interfaces are
schema-governed project products, not stock MLIR Scheme semantics. Stock passes
see only an admitted domain with accurate control/effect/resource constraints.
MemoryEffects alone does not capture Gambit's nonlocal control [MP03].

For GC lowering, retain two explicit strategies under the same runtime protocol:

- *FR frame realization:* materialize required live values into collector-known
  Scheme frame/root extents at may-relocate boundaries, call the runtime and
  reload. LLVM owns local machine optimization between those boundaries. This
  preserves the Scheme stack as a valid continuation/root authority.
- *SP native-statepoint realization:* integrate LLVM statepoints, relocated
  references and registered machine-frame/stackmap/code lifetimes with the
  collector. This is a different root/continuation adapter, not automatic from
  emitting stackmaps. Base/derived pointers and continuation capture need their
  own protocol; it may have a different cost/support domain [MP05].

The full design can compare both; FR is not mandated forever by legacy C. A
provider cannot add a collecting helper or rewrite safepoint placement without
updating the semantic root/control product and its proof obligations.

Region inference is also a substantive research route, but MLIR structural
regions are not memory lifetimes. Escaping closures, continuation reentry,
weak/finalization behavior and *collector-visible stale edges* constrain free
placement even if program code never reads the field again [MP09]. A useful
hybrid can eliminate/stack-allocate proved nonescaping objects and retain GC for
escaping/uncertain ones; a new traced-region representation needs a complete
runtime scan/update/lifetime law. Merely using Zig arenas does not supply it.

*** 6. Zig as the Native System Plane
:PROPERTIES:
:ID: aa3feb6e-a430-5428-9703-b7e71502678b
:CUSTOM_ID: 6-zig-as-the-native-system-plane
:END:

Zig is proposed as the implementation owner for one coherent native subsystem:
profile-bound physical planning, LLVM/MLIR sessions and ownership, FFI/module
adapter generation, target/object/artifact integration, structured diagnostics
and justified native execution services. Common descriptors, buffers, failure
custody and provider sessions are shared by actual consumers, not counted once
per product field. Existing Scheme containers, generated C alternatives and
mature libraries remain fair reuse controls.

A provider facade has a project-owned semantic interface: capabilities, bound
profile, input product validation, lowering/transform recipe, native realization,
owned diagnostics, emit/cancel/close and product metadata. Do not expose MLIR/
LLVM C++ object layouts or transient handles as the stable wire format. Upstream
C APIs are a useful interoperation surface but not a promised stable service
ABI. Current MLIR C interface callbacks can express some external effect models;
this reduces one possible C++ support assumption, not all dialect/pass work
[MP04]. Needed C++ registration/transform support stays in a bounded provider
implementation if selected; neither Zig nor C receives it for free.

For the AOT research candidate, select a *separate compiler-service process*
for LLVM/MLIR sessions and custom provider support. Zig's logical system plane
has two deployment domains: the compiler/service executable and the in-process
Gambit runtime SDK/entry adapters. They share versioned products/contracts, not
LLVM heaps or raw Scheme addresses. The compiler worker receives immutable
semantic/profile products and returns owned object/metadata/diagnostic products;
only the runtime owner validates, binds and instantiates them.

This gives provider upgrades and compiler failures a concrete boundary rather
than merely another linked wrapper. A dead worker must produce an explicit
failed/unknown session result and leave unpublished products unadmitted; it does
not qualify retry or generated-code execution. IPC, cold startup, duplicate RSS,
byte custody, cancellation, child reaping and parent GC-safe waiting are charged
to both C-full and Z-full. Reuse the [[file:../../../refactoring/zig/studies/njs-executor-storage-cleanup.org][existing single-owner execution design]];
do not add a second in-process child reaper. An in-process provider remains an
alternative with different failure/version/support costs, not an equivalent
isolation claim. This deployment choice does not force optional ORC/JIT or a
new detached waiting protocol before existing BW1 is independently admitted.

The runtime SDK contains no LLVM/MLIR implementation dependency by contract.
If its real build graph nevertheless shares a changed compiler/link provider,
those products still rebuild as required. A separate process/API is an actual
engineering seam, not proof of ABI stability, zero transport cost or zero upgrade
blast radius. C-full receives the same isolation/control capability in the pair.

This permits concrete C-layer retirement: selected Scheme C text/module emitters,
ad hoc layout and macro-selection owners, string command assembly and implicit
foreign root/control policy move to single declared owners. The ordinary C ABI
and any genuinely needed legacy cohort remain. Writing another wrapper around
all old paths would fail MA03/MA08 regardless of how modern its build tool is.

*** 7. Provider Upgrade and Artifact Boundaries
:PROPERTIES:
:ID: 9a8590fd-b562-5166-8e02-ead912294852
:CUSTOM_ID: 7-provider-upgrade-and-artifact-boundaries
:END:

Separate semantic export/version, runtime protocol/layout, provider recipe/build,
target features, native service host build, emitted product and live module/VM
instance. A provider-only change rebuilds its dependent IR/object/diagnostic
products. It need not regenerate unchanged Scheme semantics or rebuild a truly
separate runtime binary; actual build/link dependencies can require more.
If the runtime is compiled/linked by the changed tool/provider, those products
also invalidate. A stable manifest or unchanged filename does not waive this.

Bitcode/MLIR bytes are provider-versioned interchange/cache products, not eternal
portable AOT formats. ThinLTO cache is one upstream layer, not the source of
semantic/module/FFI invalidation truth. Global rebinding, imported summaries,
initialization, runtime ABI and source changes invalidate their actual consumer
closure. Compiled code remains distinct from a fresh lexical/phase/VM instance;
this work does not claim to remove the historical Darwin Scheme interface-
construction startup delay simply by changing the native compiler.

*** 8. Current Decision Boundary
:PROPERTIES:
:ID: 2a1fcc5a-eade-5895-ad59-565c3c54454d
:CUSTOM_ID: 8-current-decision-boundary
:END:

Adopt the full architecture as the *research candidate*, with Bmin as control.
The matrix identifies concrete LLVM reuse, real C retirement opportunities and
new semantic/runtime capabilities. It does not certify Zig adoption, speedup,
new GC/VM support or native correctness. Architecture/cost closure precedes any
implementation or native experiment. Total-vs-B0 and Zig-vs-C-full certificates
remain distinct; a local wrapper counterexample does not settle a whole-system
choice, and ambition does not turn unknown costs into a positive bound.
