native test, timing experiment, measured maintenance saving or positive economic
bound. Read the [[file:scheme-function-zig-design.org][real reverse path]],
[[file:scheme-function-zig-evidence.org][source/paper ledger]] and
[[file:scheme-function-zig-arguments.org][conditional arguments]].

**Modernization can have architectural value without proving that Zig adds net
value. The present evidence supports a real Zig backend design candidate; it
does not yet select Zig over equally modern C.** The scientific object is
Gambit's semantics, runtime protocols, native generation and measurable service
behavior. Language selection is one falsifiable engineering decision inside it.

*** Equal Capability Controls
:PROPERTIES:
:ID: f8da0612-e4e6-5bc0-a67c-72fffc335e33
:CUSTOM_ID: equal-capability-controls
:END:

~B0~ means the inspected legacy C path. ~C-G~ means modern C services with the
same Scheme-generated semantic descriptors, typed generated operations, opaque
service interfaces, mature C libraries and independent LLVM provider where
useful. ~C-ZT~ adds useful Zig tools to that C design without assuming Zig-owned
runtime services. ~Zig~ means real generated Zig hosts and/or Zig native services
with the same semantic/runtime admission obligations. C-G is not forced to
duplicate everything manually; Zig is not awarded compiler/runtime redesign
gains that C-G can share. An all-C solution may already use Clang/LLVM.

*** Quantification Without Invented Performance Numbers
:PROPERTIES:
:ID: 67424359-4528-577c-b661-510e9071b207
:CUSTOM_ID: quantification-without-invented-performance-numbers
:END:

SM13. Source-bounded counts for public reverse are in SF03/SF17. For n successful
iterations, the selected artifact schedule has n cons, n heap tests and n loop
polls; no per-iteration native recursive call is present already. Conditional
pair storage is 3n words. Therefore “Zig eliminates recursion/GC/allocation”
cannot support the economic case. Zero generated-C units for converted products
is a structural target, not zero compilation work, zero retained C units or a
prediction that macOS startup interface computation disappears.

SM14. Use a fixed maintenance horizon T and admitted capability set K. Define
burdens in agreed engineering-cost units, with runtime/build/memory/latency
outcomes separately constrained or explicitly valued; do not add seconds,
bytes and person-days directly. For each candidate include one-time design,
migration and verification; recurrent compiler/service/target upgrades;
retained C/control islands; duplicated authorities during transition; and
admitted regressions. The complete common modernization net versus B0 is a
different ledger from Zig versus C-G:

#+BEGIN_SRC text :eval never
Net_modernization(P,T,K) = valued outcomes versus B0 - full added lifecycle cost
Delta_Z(T,K) = avoided residual C-G support and maintenance
             - added Zig migration, emitter, tool, ABI and target obligations
             - extra bridge, retained-island, qualification and regression cost
#+END_SRC

Avoided C code is credited only after the replacement's domain/callers and
actual retirement obligation close; future hypotheses may be scenario inputs
but are not retired-work receipts. Shared support used by k components is
charged once, plus per-consumer adapters and upgrades. Theoretical bounds use
~lower(saving) - upper(cost) > 0~, with common uncertainty and dependencies
preserved. An unbounded cost is not zero. If outcomes/capabilities differ, report
a tradeoff/Pareto comparison rather than falsely calling it equal-capability
net benefit.

| ID / event | C-G must maintain after reuse | Zig must maintain after reuse | Necessary condition / falsifier |
|-
| SE01 Pair representation change | Scheme size recipe; generated offsets/builders; C decoder/root ABI checks | Same recipe/decoder/root checks; Zig emitter/type/layout update | Saving only if Zig removes additional manual synchronization; generated C may erase it already. |
| SE02 New force/error/control edge | Semantic operation, root/frame completion, C service/disposition realization | Same semantic work plus Zig control-island disposition/cleanup audit | Ordinary defer cannot replace continuation/nonlocal-control reasoning. |
| SE03 Module publication or VM ownership change | Common product/binder lifetime and init/cycle policy; C consumer migration | Same policy plus Zig storage/slice/lifetime adapters | Neither language proves escaped callback/continuation drain. |
| SE04 New target or host ABI | C frontend/linker/runtime profile and decoder/call tests | Zig frontend/linker profile, codegen support and tail/dispatch evidence | Unsupported required target rejects selection for K; reducing K is a separate product tradeoff. |
| SE05 LLVM/MLIR provider upgrade | Adapter/dialect/pass/IR product invalidation and runtime contract checks | Same provider obligations plus Zig FFI/build integration if present | Isolation can limit invalidation; Zig does not remove unstable API or C++ dialect work. |
| SE06 Shared byte/executor/cleanup service upgrade | Library plus wrapper/owner/cancellation/drain logic for actual users | Standard facilities plus remaining owner/cancellation/drain logic | Amortize one shared implementation, not semantic obligations; include per-consumer migration. |
| SE07 Delete legacy renderer/protocol | Show zero live caller/reference, bootstrap and independent control coverage | Same, including retained C foreign islands and newly generated Zig clients | Deleting one function does not retire module-wide emitters or global macros. |
| SE08 Bootstrap/compiler-tool upgrade | Scheme compiler closure and C runtime/native dependencies | Same closure plus Zig emitted-source/tool compatibility | Self-hosting through Zig needs complete compiler dependency domain; no automatic developer-time saving. |

SM15. *Positive Zig increment needs all of:* equal admitted capability,
bounded residual C support after maximum sensible reuse, actual eliminated
responsibility rather than a forwarding wrapper, enough necessary shared users
to amortize fixed cost, and complete tool/ABI/control/target/lifetime cost below
the conservative saving. A language feature is evidence of a mechanism; it is
not a positive cost bound. C-ZT wins when tools help without justifying a Zig
runtime rewrite. C-G wins when generators/libraries remove the residual work
or Zig's extra integration dominates. No crossover k or percentage is supported
by current source and papers.

SM16. **If Zig does not pass, continue the same modernization program in modern
C with optional independent LLVM/MLIR services.** The substantial decisions are
explicit control/root/allocation/ownership contracts, decoupled native products,
lawful higher-level optimization, and responsibility deletion with complete
evidence. This function makes that program concrete. It does not itself prove
parallel GC redesign, whole-language Zig support, native correctness, total
positive net or Zig-specific positive net.

The [[file:../../runtime/control/studies/map-scheme-zig-cost-matrix.org][map matrix]] makes explicit that C-G itself
requires generator, validator, runtime/service, migration and lifecycle work.
Shared architectural value does not imply equal or zero realization cost.
Compare each complete candidate with current Gambit, then compare them with
each other; Zig need not wait for an intermediate modern-C implementation.
