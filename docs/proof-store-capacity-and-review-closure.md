# Proof Store Capacity and Review Qualification

## Capacity Contract

ComputationalEvidence count limits use the same caller-owned policy as the
Library's other relational interfaces. Input, derived, and output defaults are
actual Scheme `+inf.0`. Candidate declarations accept `unlimited` or a positive
exact integer. The consumer transports unlimited counts without truncating
source rows. Explicit finite limits still reject over-capacity sources.

This does not remove independent structural, proof-work, allocation, request,
or execution-time safeguards. It does not make unsupported projections into
proofs or authorize a native retry.

The Library regression keeps all 1,100 input rows, obtains a real positive
support packet, preserves cache identity, rejects an explicit 1,024-input
limit, and rejects stale-generation references after source withdrawal. A new
withdrawn-source closure verifies while the removed Fact is `finite-absent`
with no positive support; restoration obtains a separately bound generation.
Zero, negative, boolean, and misspelled limits remain invalid.

## Results and Proof Boundaries

A proof-store request rejection does not erase an independently obtained query
result. The observation keeps the full source inventory, candidate, generation,
rule-source bindings, and original error. It records unknown support without
inventing support nodes. Remaining requests in the same rejected batch are not
retried. Unsupported negation/operator projection remains unsupported; a
verified positive relational proof is not a general Scheme execution proof.

## Sealed Review Lifecycle

A review validation domain uses its existing complete inventory, two workers,
and 60-second total budget. The SQLite queue commits before workers start;
connections close explicitly, and interrupted claims are never retried.
An evaluation process retains its Library runtime and query owners until EOF.
Request completion, process exit, teardown, and final source checks remain
separate obligations. All of them consume the original budget.

Explicit source-program reuse is restricted to byte-identical `sourceTexts`
and the complete source-digest inventory. It does not apply to arbitrary
constructors or compiled modules. Every new path binding is fully rehashed;
changing bindings advances the actual native source generation even when
facts are identical. Previously returned results are released, while historical
catalog objects retain their original bindings. No proof or query-result cache
is carried across that context change.

For retained requests, the owner validates the complete seal at process startup
and terminal teardown. The sealed child validates every implementation and host
tool file immediately before and after each request, and binds its response to
that exact engine ID. The parent checks its loaded code origins on dispatch and
return, verifies the exact request/response identities, and retains the raw reply
bytes even when rejected. A terminal identity error, missing/foreign engine ID,
or failed reply cannot qualify the owner or domain. Fresh workers retain the
original preparation check. A foreign owner is rejected before creating a
request directory. These are explicit lifecycle boundaries, not a metadata-only
validation cache or an attestation of the trusted host.

Seal validation still hashes every implementation and host-tool file. A single
non-following directory scan checks the complete inventory; each file retains
its individual symlink, resolved-path, and SHA checks. No metadata-only hash
cache replaces source validation. Directory-link rejection is also tested.
