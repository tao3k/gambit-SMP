# Failure, Claim and Receipt Correspondence

The consumer review DSL requires an exact `FailureBinding`, `FailureClaim` and
`ReviewedLink` join. Candidate identity, failure identity, original report path
and SHA, claim, and supporting receipt all participate. A reusable receipt for an
unrelated claim cannot establish this correspondence. `Cause` is proposal data
only. Stale inputs, missing receipt dependencies and circular justification keep
the correspondence unusable. `REVIEW_REQUIRED` is not native acceptance or host
execution authorization.

`evidence/review-links.json`, when supplied by the trusted host, uses
`failure-claim-receipt-links.v1`, the complete canonical failure inventory SHA,
and `links`. Each link names `candidate`, `candidateIdentity`, `failure`,
`failureReceipt` and `evidence`. References contain repository-relative `path`,
`sha256` and an exact RFC6901 `pointer` into JSON. Original receipts are not edited.

The evidence record uses `failure-causal-review.v1`, `domain: causal-review`,
`status: reviewed`, `claim: reviewed-causal-link:<failure>`, the same failure,
candidate identity and failure receipt reference, and three `reviews` references:
`failure-scope-review`, `change-relevance-review` and `assumptions-review`.
Each referenced review retains the same identity/reference and explicit receipt
`premises`. Missing premises remain blocking, not silently manufactured.

Python only checks schema, exact bytes and pointers and transports relations.
Scheme computes transitive usability and decisions. The host remains responsible
for the authenticity and substantive review of these statements: typed JSON or
the word `reviewed` is not a causal proof. Finite/model/local controls are not
silently promoted to review statements. No positive approvals are generated by
this adapter. Absence of the file preserves the current conservative DENY state.
