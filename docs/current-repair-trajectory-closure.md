# Current Repair Trajectory: Implemented Read Contract

## Scope

This implements the entry and association remedies in
[the retained artifact audit](current-repair-trajectory-audit.md). That audit
remains an immutable observation of the predecessor, not a claim about the
new implementation. No Gambit runtime, native fixture, source lock, budget or
implementation-task checkpoint is changed. Items 9 through 12 remain open;
registration does not award native progress.

## One Existing Entry

The existing argument parser declares the effects of `trajectory clues` and
`trajectory catalog`. They validate inputs and persist disposable read hints,
but do not acquire execution custody or initiate global retention. A read
capability is separate from authorization to run a sealed task program.

Installed Library identities are hashed at the outer API observation's entry
and exit. Nested loads reuse those identities only within the same process,
thread, seal boundary and exact inventory; they still use the native loader.
The outer exit rejects drift, including after a caller exception. Independent
requests rehash; there is no persistent valid-verdict cache or timestamp-only
shortcut. This removes repeated whole-installation hashing without moving
Scheme parsing, linking or inference into Python. It does not change native
timeouts or performance acceptance.

The provider launch receipt advertises `evidenceRead`: an exact existing CLI
command reading inert Scheme from the owner-local request file. Its basename
is configurable, and the capability can be disabled. The adapter does not
inject a query, evidence dump or investigation steps. Native execution grants
are unchanged. The controlled-provider test exercises the literal advertised
command; it is not a real Grok investigation or proof of model quality.

## Association And Source Identity

The registered Scheme association still requires all bindings on one
observation **and digest**. On a miss it can expose factor names, values and
nearby witnesses without weakening that conjunction. Values are scoped to
matching witnesses when an anchor exists. A cross-witness conjunction remains
unmatched. The caller may replace the association with its own Scheme rules;
none of these outputs chooses a hypothesis or action.

The four current-repair bundles use existing modeling/checkpoint relations.
Their clauses are counters, not native receipts. Their retained source lock is
explicitly a predecessor, and current-candidate applicability is unbound.
Per-worker error/success claims require worker, owner and incarnation identity;
VM-wide flags do not establish that conjunction.

## Unavailable Provenance Is Evidence, Not Permission To Use Old Facts

The registry can configure an `availability` Scheme source and constructor,
using the same registration mechanism as `selection`. Python supplies only
host observations: declaration identity, referenced path, expected/current
digest and missing/changed reason. The configured Scheme declaration projects
these into provenance counters. No unavailable view contributes domain facts.

Repository reads return a compact `evidenceCoverage` header for the registered
Clue views. It includes available/unavailable counts and a relational factor
for expanding provenance counters through the same query entry. Full reference
lists are not appended outside the Library's progressive evidence slice.
This coverage is not completeness of the native acceptance inventory.

Only the typed missing/changed-reference observation is isolatable. Without
the configured projection it remains an error. Invalid declarations, Scheme
components, cache aliases and escaping paths are not downgraded to missing
provenance. Strict view evaluation/materialization still rejects unavailable
references. A source changing during a read rejects that read; it does not
silently change scopes or continue with mixed versions. Restoring a missing
reference changes the source identity and requires fresh applicability checks.

An unrelated research view currently has changed references. The read contract
allows the lifecycle view to remain queryable while reporting this coverage
gap. It does not rebind the other owner's hashes or declare the full graph
qualified. Source review remains explicit and separate.

## Checkpoint And Formal Boundary

The existing Library owns selection, deltas, folding and checkpoint semantics;
Python only stores/transports the opaque read token. A fully displayed shared
clause is retained when changing scope. Repeating the resulting scope returns
no family bodies. Deferred bodies are not acknowledged. Cache loss permits
honest replay, never erasure of evidence or native progress.

Source identity is still repository-wide. A changed source can reset read
hints, including an unrelated update. This implementation does **not** claim
per-evidence retention across source revisions. Query continuation is not
execution continuation, and neither confers applicability or native credit.

Reuse the upstream `ClueQueryResume` properties `CurrentFacts`, `ExactReads`,
`CallerOwnsScope`, `NoAuthority` and `History`; reuse `EvidenceCheckpoint`'s
missing-binding, enumeration-witness and independent-support theorems. These
are abstract boundaries, not a newly proved Python-to-C refinement. This round
does not copy framework proofs into SMP or claim new QNT/Lean qualification.
The existing host-omission control exercises real host facts, Scheme inference,
Clue refresh and fresh-process continuation. Source repair remains a distinct
obligation.

## Acceptance

- A granted read works without a native program, execution lease or global GC.
- Unknown bindings expose relational witnesses; mixed identities never match.
- All four repair contracts expose concrete unsupported clauses, not false PASS.
- Changed/missing references remain queryable as provenance counters, with no
  stale domain support; strict evaluation still rejects them.
- A real source appearing/changing during a read invalidates that snapshot.
- Cross-process continuation reuses displayed evidence; interruption or cache
  cleanup cannot grant execution or native acceptance.

See [qualification and retained failures](../evidence/review/repair-trajectory-closure/validation.md)
for the exact local controls and their limits. A passing controlled provider
does not establish that a real model will choose the entry promptly, repair a
runtime defect, or use fewer tokens. Real-provider/native work is not started
from this research lane.
