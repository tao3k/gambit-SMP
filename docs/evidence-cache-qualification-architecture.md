# Evidence, Cache And Qualification

## Framework-First Contract Qualification

The current candidate uses the existing native ASCENT Module to select component
dependencies. Python binds only that selected closure; Review's configured
Catalog/Review/History program inventory comes from the existing consumer
scenario, not from every registration or a second Python linker. Scheme derives
per-contract required-input gaps, command completion and invalidation origins.
The transport returns those origins rather than reducing them to a status bit.

Read checkpoints distinguish the reading contract from the changing evidence
snapshot. Exact unchanged units can remain read while new counterevidence and
withdrawals are rederived. Restored query intent does not restore applicability,
execution authority or a fixed next action. Scoped Evidence archives validate
the selected closure with the same native loader after original source cleanup.

The durable store rejects appends after an execution terminal. That permanent
condition is not retried like a transient compare-and-swap conflict. Seals bind
the resolved interpreter binary rather than a disposable environment alias.
Framework validation uses unique completed-test events for its inactivity
watchdog, not heartbeats or total elapsed wall time. No release performance
threshold or native acceptance condition is widened by these changes.

The new Library is tested as an isolated wheel before installation into the main
SMP environment. Prior failures remain retained: omitted invalidation origins,
an over-broad registry binding, the missing configured Catalog program binding,
and the ephemeral interpreter alias. The old test that demanded invalidation for
an unselected source now checks both independence and denial after a selected
source changes. No assertion about selected-source drift was removed.

These are framework contracts, not GC fixes or new native milestones. The main
SMP installation and runtime qualification remain unchanged. The frozen framework
candidate completed its full and sealed-host checks before any main installation.

## Independent State Axes

The Python readback now separates these existing facts instead of using one
`STALE` label to infer lost progress:

| Axis | Meaning | Authority |
| --- | --- | --- |
| Recorded outcome | What the original execution reported | Retained receipt; not an unconditional proof of validity |
| Evidence binding | Whether source, patch, tools and evidence-log hashes match | Recipe inputs, observed inputs and historical bindings |
| Artifact availability | Whether declared output bytes exist and match | Disposable output descriptors and tree/file identities |
| Current producer eligibility | Whether the producer still satisfies every reuse requirement | Existing strict completed-producer validation |
| Milestone completion | Which full requirements have valid durable evidence | Existing Evidence Scheme DSL/ASCENT requirements; not cache existence |

`recipes.inspect_run` returns `recordedOutcome`, `evidenceBindingStatus` and
`artifactAvailability`. `research_kernel.inspect` propagates those facets
through the sealed receipt and exact child-receipt hash. Available, missing,
modified and unknown outputs are distinguished. Missing cache does not become
a failed original execution. Missing output and source/patch drift can coexist;
neither condition hides the other.

The legacy `identityStatus` remains fail-closed for existing producer consumers:
it requires valid evidence binding AND all required output identities. Runtime,
source-refinement and execution admission are not granted by a recorded PASS
or by the new diagnostic facets. No budget, review or native gate is relaxed.

## Strong Evidence And Patch Binding

The source/patch authority is an exact revision and source lock, including
the overlay SHA-256 and per-file hashes. Recipes declare repository inputs;
materialization binds source locks and actual patch bytes as observed inputs.
Inspection rechecks those declared and observed hashes separately from output
availability. Historical bindings must supply matching archived bytes; they
are not inferred from a filename or a missing cache. Native milestone rules
remain in `evidence/research/smp-threaded-vm-native-grid/milestone-rules.ss`.
Python must not invent a package-specific completion counter or grant a native
gate because a Quint model passed.

Repository-persisted gate evidence must retain the gate scope, fixed source
identity, patch identity, execution receipt/log hashes and original budget.
Deleting `.data/fixtures` or running `make clean` must not delete that authority.
Changing patches creates a candidate requiring requalification; it does not
silently invalidate a completed older-source milestone or qualify the new one.
A demonstrated regression or invalid original evidence can withdraw completion
with explicit source-bound causal evidence. Cache absence alone cannot.

## Executable Resumption

The current implementation extends the existing checkpoint module and research
entrypoint, rather than maintaining a second mutable progress file. Immutable
receipts and the existing journal are the stored state. Scheme rules in
`evidence/dsl/checkpoint.ss`, registered through the existing component catalog,
derive these distinct relations:

| Relation | Required evidence |
| --- | --- |
| `historical_complete` | Authenticated successful stage and complete successful ancestry |
| `satisfied` | Historical completion applies to current input bindings |
| `reusable` | Satisfied stage, observed parent quiescence and available typed outputs |
| `historical_only` | Retained generation evidence without live output bytes |
| `artifact_unavailable` | A historical pass whose typed output is not currently available |
| `invalidated` | Historical completion does not support the current bindings |
| `unresolved` / `failed` | Missing completion or retained failed outcome, respectively |

Python verifies custody, hashes, receipt ancestry and output availability. It
transports these facts; Scheme derives the decisions. Stage identities are data,
not a hard-coded twelve-item list or a model-directed next action. The returned
scope explicitly distinguishes recipe stages from cumulative SMP milestones.
Origin recipe/engine/input identities accompany the checkpoint; requested-target
identity matching remains an independent execution check.
The transport also requires a terminal recorded PASS before returning REUSED;
an erroneous policy answer cannot upgrade a failed origin into a success.

Repeating `research --run` with the same completed run directory now validates
and consumes the original result with `resumeStatus=REUSED` and
`executionLaunched=false`. It never overwrites that receipt or relaunches its
bootstrap/tests. A failed run returns its successful checkpoints and unresolved
stages without implicitly retrying the failure. Available generations remain
consumable through the existing `gambit.completed-runtime` capability.

When the final receipt was never written, the existing committed stage journal
is authenticated against its immutable observation store. Readback returns
`COMMITTED_PREFIX` / `INCOMPLETE`, retaining successful stages and original
dependencies. It does not reconstruct a terminal receipt, infer a process exit
from a reboot, or grant execution while parent completion is unobserved.
Missing custody is unknown evidence, not an invented zero progress count.

Cache deletion cannot delete `historical_complete`; source changes invalidate
applicability rather than rewriting historical results. Artifact reconstruction
is distinct from repeating qualification. This change does not automatically
derive the minimum recompilation closure for changed runtime/compiler code;
that requires an explicitly bound dependency/qualification graph. It also does
not turn an incomplete parent process into a safely consumable runtime.

## Durable Execution Continuation

The current downstream adapter imports the registered upstream
`evidence-checkpoint-fragment`. Scheme computes applicability, dependency-closed
consumption and unresolved requirements; Python authenticates observations,
transports facts and executes an explicitly requested Recipe. No milestone list,
stage ordering recommendation or model-selected next action is embedded in the
adapter. The completed-outcome vocabulary and storage location are declarations
in `evidence/dsl/checkpoint.ss` and `evidence/dsl/storage.ss` respectively.

The existing observation store now carries an atomic, hash-linked execution
prefix. Its default configured location is `.state/reasoning/history.sqlite3`,
outside disposable `.cache`. Migration uses SQLite backup and retains the old
database bytes. Checkpoint append and immutable observation publication share a
transaction; competing processes cannot overwrite the same prefix. File
publication follows this commit, so a killed publisher can leave recoverable
evidence without a final cache file. The local state database is not a Git asset.

Process births are recorded before launch and associated with their observed
PID and boot identity. Recovery distinguishes actual terminal completion from
currently observed process-group absence. An incomplete producer stays
INCOMPLETE even when its groups have exited. A pending birth without sufficient
observations stays unknown. Safe stage consumption does not fabricate an old
terminal PASS, renew a failed stage or grant new execution authority.
