# Result-mutex delivery: a bounded mailbox and scheduler-handoff refactor

2026-10-23. **Design and finite-model research only; native remains 8/12.** The subject is one synchronous result-mutex sender and the scheduler transitions needed to deliver its thunk. Lifecycle join, TYPEID and release are not composed into this claim. No runtime, compiler, Recipe, timeout, processor count or native inventory is changed.

## Recommendation and why it is larger than another routing branch

Prefer an **authoritative thread mailbox, rooted claim and acknowledged scheduling handoff**. A thread-targeted request is never linked onto a processor's high-level request queue. Its only pending chain is the target's existing interrupt queue under the target lock. Removing the queue node must acquire a live dispatcher/continuation consumer before the queue root is withdrawn. Notification carries no request node. The transition that makes a thread noncurrent, and the transition that lets its processor sleep, must preserve a concrete route to service pending work.

This is not the already-failed “thread queue plus OTHER” variant with a new name. That variant scored 5/8 and was reverted. The additional change is a common **scheduler commit protocol**: a thread cannot commit an ordinary blocked state over unclaimed mailbox work, and a processor cannot commit sleep based on an obsolete runnable-publication observation. After a wake byte is consumed, the scheduler re-evaluates the durable runnable state before waiting again. This requires reorganizing a few boundaries together; it is not honestly a one-line or one-branch repair.

The intended trade-off is a little explicit per-processor bookkeeping and concentrated scheduler code in exchange for one queue owner, no full-processor routing scan, and no probabilistic rescue/retry schedule. It reuses Gambit's existing target lock, processor lock, run queue, continuation representation, result mutex and device abort primitive. It does not introduce a global dispatcher lock, another GC, native strong-root registry, lock-free reclamation system or a different pthread_join policy.

The proposal is **not yet a demonstrated native root-cause repair**. The first native writer that strands the reported node remains unbound. This design removes an ownership split and supplies the missing delivery contract independently of a guessed writer. It must still refine the actual source and preserve the existing API before implementation can be justified.

## Concrete ownership protocol

Keep the existing two-slot request `[next, result-mutex]` and ordinary result-mutex name/thunk/specific semantics initially. No new per-request envelope or global request serial is required in the production fast path. Model identity is logical; any diagnostic ID is a separate, optional instrumented build concern.

1. **PUBLISH.** With target lock held, link exactly once into its thread interrupt queue. The node starts detached. Construction or the one allowed queue pop is the source of that detached ownership. If the target is noncurrent, preserve `migration-target`/pinned destination when publishing its runnable entry. Publication remains rooted through existing Scheme objects.
2. **NOTIFY.** Release the target lock, then request a legal checkpoint on the observed processor, or abort the destination processor's wait after runnable publication. This operation never edits `request.next`, `head` or `tail`, and never passes the result-mutex node to `raise_high_level_interrupt_pstate`. A notification to an old processor is harmless only if migration/restore inherited the pending mailbox obligation.
3. **CLAIM.** At a legal interrupt/resume/scheduler checkpoint, acquire target lock, capture node/result mutex into a GC-described activation, remove just that node, clear its next and release lock. Only then call the thunk. A masked collective may defer claim, but must preserve the queue; it must not run ordinary Scheme callbacks while holding scheduler locks or inside an illegal GC context.
4. **EXECUTE AND REPLY.** Use the existing thunk result store and result-mutex unlock. Result storage, mutex unlock, sender runnable publication and caller consumption remain distinct events. The dispatcher/continuation root survives callback GC and supported suspension until its last use. Target termination continues to use the existing abandoned-mutex contract; no invented success, global once bit or replay is introduced.
5. **BLOCK COMMIT.** Before making the target noncurrent and committing an ordinary wait, inspect its pending mailbox under the same thread lock that protects publication. If work is pending, preserve a runnable/resume route that drains it; retain the original operation's retry semantics. Existing mutex-lock void-resume retry is relevant. A pre-check outside this commit is insufficient.
6. **PARK COMMIT.** Before a processor enters device-less wait, register preparation and observe runnable publication state. Runnable publication and the decision to commit sleep share the destination processor's synchronization. A changed generation/ready state cancels sleep. If sleep is already committed, publication leaves a persistent wake. On return/byte consumption, revalidate durable readiness before another wait. The OS select implementation and its timeout need not be rewritten; its admission protocol must be coherent.

The mailbox owns **unclaimed** delivery only. A claimed callback may legitimately block or wait on a nested request while its continuation remains rooted; it must not be counted as permanently unclaimed mailbox work. Conflating pending, active and replied would replace loss with busy waiting or deadlock.

For park bookkeeping, the candidate model uses a publication generation and a prepared generation under the existing processor lock, plus prepared/committed state. If current synchronization can implement the same invariant without new fields, prove that reuse first. `scheduler_status` is documented as startup pending/ready/failed; it must not be silently reused as a parking bit. Otherwise append private scalar bookkeeping to processor state with constructor/reset coverage and coherent same-producer recompilation. These are not Scheme references and need no new raw-root ABI. Counter overflow/reuse needs an explicit rule; the finite model does not solve wraparound.

## Learning from the mature runtimes without importing their architecture

Pinned local OCaml `46e1c324…`, `runtime/domain.c:159–183,412–450` separates a durable pending predicate from interrupt-word notification. `caml_send_interrupt` publishes pending, broadcasts under the recipient lock, then requests a poll. The backup-thread wait at1182–1197 and domain-start wait at1523–1535 recheck pending under the same lock used around condition waiting. This supports the **predicate + acknowledged responsibility + wait synchronization** pattern; it does not prove Gambit's masked self-pipe/select protocol equivalent. OCaml's backup threads service STW, not arbitrary Gambit thunks; adding them would expand this task unjustifiably.

Pinned local Chez `41d5ffca…`, `c/thread.c:158–184` publishes the thread in the population before rereading collect-request pending and setting its trap; the comments explicitly identify work that may arise during publication. `S_activate_thread`/`S_unactivate_thread`209–235 preserve exact acquired activation effects. The transferable lesson is to recheck durable responsibility at publication/activation boundaries, not to copy Chez's collector or claim that a trap bit itself delivers a request.

These local source reads are pinned/hashes retained in the research receipt. They are design references, not models of upstream runtime behavior.

## Finite QNT value and its explicit envelope

New research candidate `result_mutex_mailbox_handoff.qnt` leaves the existing measured-failure model untouched. It represents one sender, one target, two processor identities, one bounded target block, one migration, one masked interval and one park attempt per processor. Queue membership, rooted activation, ready owner, running owner, sleep preparation/commit, publication generations, wake availability, actual thunk execution, reply and consumption are separate fields.

It has **no arbitrary drop action** and no hand-written `reachable=false` loss step. Claim removes the queue node only while acquiring its activation consumer. `noLost` is derived from outstanding wait versus mailbox/activation ownership. A second predicate, `serviceable`, detects a pending but still-reachable node whose target has no running/runnable/wake path. This distinction matters: preventing physical loss alone can leave a sender waiting forever.

Four positive initializers exercise running, already-idle, migrating and prepare-vs-publication races. `completion` is checked under explicit weak fairness and bounded terminating callback/masked interval. Six mutations remove the pending-aware block commit, claim root, wake/debt recheck, park validation, destination preservation or execution-before-reply. Decoded witnesses must identify their actual bad fields; root safety, serviceability and result correctness are not interchanged.

Finite model progress is not a time bound, native GC proof or arbitrary scheduler fairness. More than one request, repeated epochs/wraparound, unbounded suspension/reentrancy, cancellation and exception paths need refinement or additional scoped models before broad production claims. The old failed model profiles remain negative evidence; the new positive candidate does not retroactively make any 5/8 or 7/8 run green.

## Performance contract and the next admissible decision

The desired performance envelope starts with the existing 100000 sends, ten synchronous senders and -:p11 topology, retaining the existing limits and baseline identity. Enqueue and claim do constant link work; ready publication/park validation add constant bookkeeping under locks already required for that transition. There is no per-request full-processor scan, global strong-root table, timed polling, retry-until-lucky rescue or per-request extra allocation in this minimum design. Per-processor metadata is O(P); outstanding synchronous requests remain bounded by participating activations only when their nesting/workload bounds are stated.

Callbacks, GC rendezvous, lock contention, scheduler delay and FIFO head-of-line blocking still cost time. A batch cap B may bound dispatcher monopolization, but adopting it changes service scheduling and would need its own source/order proof; it is not silently included in the minimum candidate. Neither QNT state counts nor “O(1)” establish native latency or throughput. Benchmark/acceptance evidence must measure the same producer, topology, heap, natural exit, wake/syscall/lock work and original budgets; no widened timeout or reduced processors.

Source correspondence for the current tree is `evidence/research/smp-retirement-study/result-mutex-mailbox-handoff-correspondence.md`. It binds publish, notify, claim, block commit, and park commit to the existing lock order, ticket-lock atomics, select abort, and the current-to-noncurrent sites. Claim GC maps and a thunk exception that skips unlock stay unbound. The census shows more than one suspension site, so the candidate is not a single bounded edit. Do not implement from the QNT pass alone.

Before implementing: complete the source transition census and lock/memory-order refinement, root/continuation/error coverage and exact park-generation/reset semantics; reject the candidate if those require an uncontrolled rewrite. Only then make one coherent bounded source change and compare against the saved 7/8 producer under the existing local flood protocol. Full first-eight qualification still belongs to the changed producer before any broader production claim. A flood8/8 remains a local test; two same-contract task receipts are still needed for9/12.
