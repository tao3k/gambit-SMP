## Decision: no additional catch, no broader lifecycle prerequisite

The existing chain already proves a real invalid GC header access and a real result-mutex wait class. It does not yet prove their first causal writer/owner transition on one current producer. Repeating abstract ownership models, broadening retirement, or wrapping exceptions cannot close that gap. The previous twenty assembly controls narrow how to trust a record, not how to fix Gambit. The two diagnostics below are the last necessary **measurement boundary**, not a substitute runtime repair.

For request delivery, the recommended structural repair is to remove the moving request node from the processor notification path: thread-addressed mutex requests have one thread inbox; processor notifications carry only a service obligation/hint. Commit the node under the thread lock, retain it through actual dequeue into the dispatcher activation, then let the existing result-mutex completion/abandon path settle the sender. Running, migrating and waiting must not select a second mutable next-link owner. A level-triggered pending inbox condition must also survive park/notify races until an actual service attempt; an interrupt bit alone is insufficient. This is a repair boundary, not another catcher or a new global coordinator.

This recommendation **removes a structural alias opportunity**. It does not establish that aliasing caused the retained7/8 failure. Prior thread-only5/8 and8/8-then4/8 results are specifically why inbox conversion without complete wake/park handoff is not a sufficient fix. The retained aggregate930553 and empty heads do not identify the pending request or prove it was lost. Do not implement another thread-only variant and claim this recommendation has been tested.

## Carrier: survival has an owner outside the crashing runtime

The current candidate has no implemented gc_diag carrier. `setup_mem_pstate:5042`, setup_mem_vmstate5177 and cleanup_mem_pstate5589/cleanup_mem_vmstate5607 are actual state lifetime boundaries, not an existing crash-output API. Debug ps->mem fields and Scheme heap/RC are not a post-exit carrier. The diagnostic output's final consumer must be the owned harness reader, after all writer processes are quiescent, **not** the runtime cleanup function. No Scheme root or lifecycle pin is needed for raw mapped diagnostic bytes.

Within the already proposed bounded shared-output artifact, choose a fixed-size regular task-owned file with a reader mapping held by the supervisor and a distinct child MAP_SHARED mapping of the same object. Bind actual object identity, size, schema and run nonce before allowing writes. This concretizes the existing carrier proposal; it is not an implementation claim or a new transport. No per-record syscall. Do not silently truncate/reinitialize the file on repeated setup, VM recreation or processor-slot reuse.

[Apple's mmap manual](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/mmap.2.html) distinguishes MAP_SHARED from MAP_PRIVATE and notes that close does not unmap. This supports the object/view distinction; it does not certify this proposed harness wiring. RAM visibility to a surviving reader is the present requirement. Disk/power-loss durability is not required or claimed; msync/fsync is not a substitute for correct mapping ownership or the hot-path Store/Load order.

DMB is therefore insufficient without five other facts: actual shared backing identity, a surviving reader-owned reference, no premature clear/truncate/reuse, complete single-writer record/context publication, and a quiescent reader boundary. Even DSB cannot create an external owner for bytes stored only in the child's private heap. A stronger barrier may be evaluated only against actual target semantics and controls; do not add barriers indefinitely instead of fixing ownership.
