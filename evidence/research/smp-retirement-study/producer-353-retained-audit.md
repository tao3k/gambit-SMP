## Actual Retained chain: preserved reachability without a completion owner

The request is `[next, mutex, target, phase, states, R-unit, capability]`. R-unit slot 0 is the one-shot responsibility pin; slot 1 is pending notification destination D; slot 2 is the VM Retained link. Request slot 0 remains the thread/detached queue link. These are distinct links and must stay distinct.

1. `##thread-intr-execute!` (`_thread.scm:1712–1743`) calls release-finish in its body and dynamic-wind after-thunk. A terminal phase alone does not settle R.
2. `##thread-intr-drain!` (1745–1779) skips non-Queued nodes and only unlinks terminal 3/4 when R is settled. A phase-5 node or terminal node with pending-D therefore stays rooted in a live target queue, but this drain does not retry its finish operation.
3. `##thread-end-locked!` (2120–2159) detaches under T, releases T, saves each successor, attempts Abandon, and publishes unresolved nodes with `##thread-intr-retain!` before clearing request slot 0. Its frame maps cover the intervening wait.
4. `##thread-intr-retain!` (1628–1666) publishes onto scanned VM slot 2 under the VM lock. Source references to this accessor are definitions, initialization and this publisher. No current consumer drains/retries/unlinks that VM chain. `_thread.c` likewise contains publication and initialization, not a generated recovery routine. `delivery_fault=1` neither executes recovery nor roots a missing request.
5. `##thread-intr-release-unit!` (1810–1814) CASes unit[0] from 1 to 0 before `##delivery-unpin!`; native `___delivery_leave` (`setup.c:275–285`) subtracts one responsibility. This pin drop is not removal of VM slot 2. A settled but still linked request stays strongly reachable.

Thus there is no implemented final consumer to name for Retained roots. This is a concrete missing edge in this producer, not evidence that every earlier flood hang used that edge.

Two additional source defects prevent simply adding a retry loop:

* **Pending-D retry is missing:** release-finish 1605–1616 returns disposition 1 immediately when native status is MOVED and unit[1] remains set. A successful native commit followed by abort failure reaches precisely that shape; repeating the whole release sees the already-changed mutex owner and reaches MOVED. Neither the second dynamic-wind finish nor the ordinary drain retries the notification. The preserved destination must be serviced independently of repeating the mutex transaction.
* **Bounded duplicate scan can make a cycle:** retain 1649 treats `guard>1024` as absence and prepends the existing node. If R is deeper than that point, R.next becomes the old head, making a cycle. At index 1025 the identity check still wins; the witness must put R deeper (for example tail index 1029 in a 1030-node list). Invalid links also become false/absence rather than a distinct corrupt-chain result. Exact absent/present/fault outcomes must replace this inference.

Native RETAINED is not synonymous with a transient lock conflict. `setup.c:1017–1023` sets phase 5 when the owner chain has a self-linked mutex; contention instead returns RETRY. An invariant-broken owner chain cannot be repaired by blindly re-running unlink or decrementing a pin. A recovery worker must distinguish retained corruption from a safely retryable notification debt.

## Grok implementation order within the existing delivery design

Do not rework join, lifecycle, select, migration or a new coordinator framework to address these edges.

1. **Give pending-D its own idempotent finish operation.** In release-finish, inspect an existing pending-D before deciding MOVED means completion. After validated mutex commit, retry only finish-notification; never overwrite payload, select another waiter or invoke the thunk again. Clear D only after the chosen notification/service contract has actually accepted the responsibility. EINTR handling needs its existing backend guarantee or an explicit bounded retry; a constant comparison alone is not a completion witness. R becomes settled only after that acceptance and one unit CAS. Permanent notification failure must retain its owner and report unresolved failure, not pass a completion test.
2. **Make Retained membership exact.** Keep R-unit slot 2. Replace the 1024 fallback with an exact lookup whose malformed/cyclic outcome refuses publication and preserves the caller anchor; never infer absence from truncation. If bounded service is required, add a per-request membership/claim field under the same VM lock rather than using a scan cutoff as a membership test. An already-linked request returns idempotent success without changing its successor. Do not treat a malformed unit as successful handoff in termination.
3. **Add the missing consumer to `##thread-intr-service-unlocked!`.** Use the existing unlocked service point, not a timer/GC under T/M/P/VM locks. A single consumer claim per VM must be nonblocking; another service attempt skips it. Keep the list linked in VM slot 2 while the claimed current node is additionally rooted in the consumer activation. Read claim/next under VM lock; release VM lock before native try-release, SYNC or notification. Do not hold a VM lock over a retry. A bounded pass skips an unresolved node and visits other entries so A cannot prevent B/C completion. Guard the pass by the membership boundary observed at entry; newly appended requests belong to the next pass. Every yield/SYNC must have generated maps for current, successor and VM association.
4. **Classify the operation before retrying it.** Terminal 3/4 plus pending-D permits notification-only finish. A detached request whose target is actually terminated permits idempotent Abandon using the existing mutex-owner recheck; verify the target terminal state and ownership under the same native locks. An Active/live request may not be abandoned by a different service activation just because it is retained. A phase-5 broken owner list stays rooted/pinned with an explicit integrity fault until that structural cause has been fixed; it is not an auto-repair success. Do not replay a lost normal outcome: current Retained storage does not preserve the local outcome/grant as a durable retry intent. If a recoverable normal-release retry needs those values, store that exact intent in a scanned request-owned field before the first fallible operation and generate its maps; otherwise preserve failure instead of manufacturing a result.
5. **Unlink only the exact settled entry.** Reacquire VM lock, rescan/revalidate membership and identity, then change head or predecessor's R-unit[2]. Preserve unrelated concurrent suffix additions. Clear only this entry's retained link/membership, release VM lock and drop the consumer activation root on return. Never clear VM head wholesale. Phase is not enough: require R settled, notification debt discharged and no remaining worker claim. A consumer claim/root is released last among its own users; the normal execution activation or existing VM execution custody must still protect native VM accesses after the last responsibility decrement. Audit that lifecycle guard rather than assuming the counter protects code after its own final decrement.
6. **Keep setup/teardown honest.** `macro-vm-init!` currently writes retained head #f. A repeated setup cannot erase outstanding membership or in-flight consumer ownership. Teardown may complete only after responsibility/consumer debt and retained roots have genuinely drained; permanent failure must preserve or explicitly terminate the VM according to the existing failure policy. Never reset a fault/counter/head merely to obtain a green close.

This is the bounded recovery change needed next. It removes the missing-consumer and notification-retry transitions; it does not explain TFIB's first illegal scan or prove recovery from a corrupt owner list. Finite scheduling and finite callbacks remain progress assumptions. Permanent OS failure has a safe unresolved outcome, not a promise that every request can succeed.
