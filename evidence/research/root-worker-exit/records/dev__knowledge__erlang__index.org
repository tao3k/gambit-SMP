* Mechanism, mismatch and candidate inference

The [[file:../../refactoring/modern-c/models/sysml/root-worker-exit.sysml][SysML learning records]] are the maintained fact/mismatch/inference/counterexample
matrix, rendered in the [[file:../../refactoring/modern-c/root-worker-exit.org][modern C architecture study]] and its [[file:../../refactoring/modern-c/diagrams/root-worker-exit.svg][D2 view]]. They are
checked by the same [[file:../../modeling/ascent/root-worker-exit.rules.scm][ASCENT policy]]; a reference-runtime fact grants no Gambit
source or native evidence. The canonical [[file:../models/sysml/learning.sysml][knowledge learning boundary]] still applies.

| Reference path | Specific learning question |
|---+---|
| =erts/emulator/beam/erl_process.c= | How does scheduling distinguish the executing scheduler from the selected process, and where are locks and progress reporting used? |
| =erts/emulator/beam/erl_gc.c= and =internal_doc/GarbageCollection.md= | Which roots and heap ownership make process-local generational copying possible? |
| =erts/emulator/beam/erl_thr_progress.h= and =internal_doc/ThreadProgress.md= | Which readers must report progress; which unmanaged readers need explicit accounting? |
| =erts/doc/references/erl_nif.md= | What can remain live after logical process exit, and why can dirty-native work still delay process GC? |
| Gambit =lib/_thread.scm= and =lib/_fifo#.scm= | What does enqueuing the original Scheme payload imply for shared mutation, GC roots and cross-context control? |

Learn the separation of scheduling, authority, progress and physical lifetime.
Do not infer that an Erlang process heap equals a Gambit execution context, that
dirty schedulers stop arbitrary C writes, or that shared Scheme values can be
copied without changing alias semantics. Multi-shot continuation and native C
return constraints remain Gambit obligations. Similar actor-facing APIs do not
prove shared implementation history or identical memory models.
