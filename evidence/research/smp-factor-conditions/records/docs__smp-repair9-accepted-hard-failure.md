## The callback error is a service boundary, not a VM-exit command

`setup.c:280–318 service_procedural_interrupts_pstate` pops a header under `procedural_interrupts_mut`, releases that mutex, calls `execute_fn(header,TRU)`, and on non-NO_ERR breaks past the reacquisition into an unconditional unlock. That last unlock is the confirmed static defect. The callback has already received ownership; the loop must not read its header again after return because the callback may dispose it.

The caller `___service_interrupts_pstate:323–352` only compares the result with NO_ERR. Non-NO_ERR leaves `intr_flag[code]` set, sets STACK_TRIP again and returns FAL. It does **not** propagate the callback's payload as a Scheme exception or terminate its target. Clearing the flag, replaying the just-executed header, or escalating every non-NO_ERR into VM shutdown would change this behavior.

The smallest proposed correction is an immediate `return err` on the unlocked non-NO_ERR branch, retaining the existing locked success/empty epilogue. No new field, ABI, allocation, lock acquisition or node dereference is needed for this correction. The remaining head/tail stay protected by the existing mutex; the caller retains service debt and will acquire that mutex on the next service. Reacquiring solely to reach the old epilogue is possible but adds contention without an ownership benefit. This proposal is not implemented or natively qualified. A callback doing a nonlocal C unwind never reaches the return branch; this fix does not cover it.

The proposed scalar fault observer may release its record only after both the writer has published its wake outcome and the receiver/terminal coordinator has consumed it for the same instance. FD closure must wait those consumers; pthread_join occurring after workers already close OS resources is not by itself an FD grace proof. Do not store arbitrary callback SCMOBJ in a native fault scalar; either retain a proper scanned owner or normalize an immediate diagnostic. Normal callback deferral needs no such stored payload.

## What a permanent wake failure can and cannot promise

Acceptance, wake outcome and request completion are distinct. EINTR retries keep the publisher claim; EAGAIN means a pipe notification is already present, subject to receiver recheck; hard errors retain accepted queue ownership and a fault obligation. The observer must run outside T/P/native queue locks, under a valid mapped Scheme activation or a valid owner-specific C terminal boundary. Remote `##thread-end!` uses thread interruption again. Worker `___run_and_throw_error_on_processor_0:927` invokes `on_all_processors`, which raises SYNC_OP through the same abort machinery before the collective. Neither is an independent rescue for an asleep peer whose only wake pipe has failed.

There is therefore no source-supported implication from "sticky fault saved" to "all accepted requests finish". Two explicit contracts are possible: retain the VM/resources and report noncompletion to a valid host supervisor (safety only), or provide an independently guaranteed wake/terminal mechanism and a fully refined landing/disposition protocol (conditional progress). Process death disposes address-space resources but is not an in-process reply or proof that 9/12 succeeds. The failure policy must be chosen and tested; silently treating retained/fatal state as recovery would erase the actual gap.

## Finite model and sufficient conditions

`accepted_interrupt_terminal.qnt` is a small **contract projection**, not a composition proof with the prior mailbox/GC models. It adds two accepted obligations, callback-error service debt, ordinary abandonment, proposed VM landing with job-failure suffix, writer completion, marker finalization and resource closure. Five positive profiles include hard-wake retention (safety only); eight negative profiles cover cleared debt, executed-header replay, primordial fake abandonment, lost job suffix, early FD close, early marker kill, failed-cleanup free and lost active root. VM landing transitions are implementation requirements, not assertions that current source already has them. A fair completion check on the hard-wake-retained profile should fail and is recorded separately as a required liveness counterexample, never as an accepted completion.

New model execution is deferred while production custody is live. No typecheck/TLC/trajectory result is claimed for these bytes. Existing external admission/disposition checks remain pending too. Preserve original caps and previous receipts; no timeout increase or model Boolean can install a missing safe point.

Sufficiency needs all of: authoritative mailbox ownership plus runnable/park and acquire publication; current-instance wake responsibility through final consumer; local callback lock correction with unchanged deferral semantics; mapped root coverage through actual execution/authorized ordinary abandonment; explicit primordial/VM terminal contract with callback suffix, all-path invocation finalization and old-cohort GC/last-consumer closure; and an available progress mechanism for any failure claimed recoverable. Source refinement and same-producer native acceptance must then validate those premises. The local unlock correction is independently small; universal hard-failure recovery is not established by it or by the retained-state model. These remaining concrete gaps still prevent a safe 9/12 sufficiency claim.
