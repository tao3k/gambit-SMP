# Quantitative Ledger for Zig and LLVM Modernization

Date: 2026-10-20. Design quantities and acceptance criteria, not benchmark results.
[Architecture](zig-llvm-runtime-modernization.md) / [evidence](zig-runtime-modernization-evidence.md).
No implementation or performance validation. A positive number below is not an
estimate unless explicitly identified as arithmetic under hypothetical inputs.

## Attribution and Comparators

Use three comparators: **B0** existing source-bound C/Gerbil construction/runtime;
**B1** the same new contracts, generated adapters and algorithmic changes carried
by C/existing tooling; **Z1** those contracts carried by Zig. Compare identical
work and correct results. B0-to-Z1 measures the whole modernization; B1-to-Z1
isolates the incremental language/subsystem choice. MLIR services have a fourth
comparison: the same semantic profile with/without each admitted transformation.

Record baseline, candidate, units, workload/coverage denominator, source/tool
identities, correctness gate, measurement method and unresolved reason per row.
All runtime/maintenance baselines below remain unknown unless explicitly cited.
Targets of zero or 100% are proposed admission requirements, not achieved values.

## Eighteen Benefit and Cost Rows

| ID | Benefit mechanism and owner | Quantity / denominator | Concrete acceptance criterion | Present evidence / limitation |
| --- | --- | --- | --- | --- |
| Q01 | One effective native resolver; R0 | Active resolution owners and live legacy callers per supported mode | One authoritative resolver; zero managed calls delegated back to retired shell templates | M1-M12 source map exists; no managed path retired by this study |
| Q02 | Less repeated C preprocessing; staged artifacts and declared units | Generated C/header bytes, preprocessed tokens and preprocessing invocations per identical semantic change | Same semantics; fewer real preprocessing/generation operations after a qualified reuse hit | No measured Zig reduction; changing CC does not remove source-level repetition |

| Q11 | Safe blocking without delaying GC; runtime participation + F2 | GC request-to-service and runtime reacquisition p50/p95/p99/max, with failures and deadlines | Meet a separately chosen latency budget under declared blocking/interrupt schedules | No numeric latency budget or speedup established here; framework timeouts are not product SLOs |

| Q17 | Reusable capability and validation infrastructure | Independently implemented target/provider adapters, shared mechanics, total semantic compatibility cells | Reuse transport/ownership/checking once; retain every required semantic/platform compatibility cell | A common protocol does not turn all producer/provider pairs into one proof |
| Q18 | Retirement and semantic acceptance | E-row passes / 32, M-item closure / 12, full native/profile denominators | All required rows closed on a coherent profile before retirement/publication | This design admits zero new E rows and closes zero M items; no performance pass inferred |

No rows may double count the same removed work. For example Q02/Q04 overlap if
cached objects are the reason preprocessing disappears; Q07 and Q13 can overlap
when fewer allocations reduce GC work. Q16 hours must not also be booked as Q17
capability value without a separate cost model. Acceptance failures and unknown
denominators stay visible, not dropped from ratios.

The [Gambit-centered BC/BG/BH design](gambit-centered-backend-redesign.md)
adds concrete backend denominators to Q02/Q06/Q07/Q09/Q10/Q17: emitted C bytes,
preprocessing work, host size, local/cross-backend jump counts, bridge cost and
root flush/reload traffic. Compiler implementation memory and the emitted
program's managed heap are distinct; sharing the Gambit runtime can avoid a
second collector without avoiding its ABI obligations.

## Arithmetic Bounds Before Measurements

For removable baseline time fraction `f`, even perfect removal has upper bound
`S = 1 / (1-f)` before any new overhead. For a parallelizable fraction `p` on
`n` workers, ideal `S(n) = 1 / ((1-p)+p/n)` before synchronization, imbalance,
memory bandwidth or service overhead. These are hypothetical sensitivity
calculations, not Gambit forecasts:

| Assumption | Arithmetic bound |
| --- | --- |
| Remove 10% / 25% / 50% of original elapsed work | 1.111x / 1.333x / 2.000x |
| Parallel fraction 20%, eight workers | 1.212x |
| Parallel fraction 50%, eight workers | 1.778x |
| Parallel fraction 80%, eight workers | 3.333x |

The reported roughly five-second pre-first-compile interval has no established
exclusive removable fraction. It cannot be assigned to C macro preprocessing,
dyld, interface construction or Zig savings without phase evidence. Nor can
these rows be multiplied together as independent gains.

For a foreign batch, use
`T = transitions * transition_cost + converted_bytes / effective_copy_rate +
native_work + queue_wait + runtime_reacquisition + cleanup`.
This exposes why batching can help even when copying is mandatory, and why a
small call can lose after introducing a service. Root publication and F2
participation are correctness work until a stronger protocol proves removal.

For the runtime, report wall time, total CPU, allocation/live volume, pause and
request-service latency, memory and failed/timeout cases together. Partition
time into nonoverlapping mutator, GC work, synchronization, FFI and other phases
before attribution. Match VMs, workers, core budget, graph shapes, compiler,
flags and inputs; collector CPU and mutator overlap cannot simply be added as
wall-time savings. No such measurements are run in this research phase.

## Cost and Adoption Equation

Over an explicit horizon, use `net = removed duplicate work + independently
valued admitted capability - migration - recurring toolchain/service/adapter
cost - regression/incident cost`. Prices or maintainer hours must come from
actual records; unknown remains unknown. Keep performance, reliability,
maintenance and new capability as separate ledgers rather than one invented
unitless score.

Reject an adoption story that retains every old path, adds Zig plus LLVM/MLIR
version axes, and earns only a new wrapper. Acceptable leverage requires a
named owner/replacement, reduced repeated work or new admitted capability, and
an incremental case against B1. No runtime component is selected for a rewrite
solely because it is C.
